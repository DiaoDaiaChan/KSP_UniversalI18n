## 0. 一句话

v1.5 换的不是算法，是**真相源**：以前问「源文件里有多少英文」，现在问「这台机器屏幕上出现过多少英文、命中了几条」。

## 1. 为什么以前会漏：三条结构性来源

### 1.1 身份错位：字典键是源文件哈希，屏幕上却是合成文本

**机制**：字典行的键 `h` 是 `fnv1a64(normalize(s))`，而 `s` 来自源文件 / IL 字面量 / cfg 原文。运行时真正渲染的文本是 **ModuleManager 打完补丁后的合成结果** —— 只要一句被 `@description` / `@title` 改写过，哈希就对不上。

**取证**：

- v1.4 专门加了 `harvest_cfgcache` 通道（读 `ModuleManager.ConfigCache`，按 `title` / `description` / `displayName` / `manufacturer` 字段直读补丁结果）。**这个通道的存在本身就是证据**：源定义与最终渲染不是同一批串，得单独再采一次。
- `src/UI18n.Runtime/ConfigLoader.cs:15` 写明「Packs 根下平铺的 jsonl 运行期永不读」。所以「在 `packs/pool.jsonl` 里有译文」不等于「屏幕上能出中文」——[reports/root-cause-1.3.md](../reports/root-cause-1.3.md) §1.2 正是用这条把 10 条池内命中判成**不算覆盖**。

**后果**：翻译工作量按「源文件行数」计量，屏幕命中按「合成文本」结算，两者没有共同分母。RO / RP-1 上这种改写属常态，于是出现「包翻了一大堆、屏幕照样英文」。

### 1.2 无度量的布尔过滤：判错的串连正文都不留

**机制**：1.4 的捕获端是两层布尔判决，两层都只留数字、不留原文。下表记的是**当时**的行号 —— 前三行那个 C# 丢弃点本轮 T-A 已经整体删掉，要复现旧行为得 checkout v1.4。

| 层 | 位置（1.4） | 丢弃型判决 | 痕迹 |
|---|---|---|---|
| C# 运行时 | `src/UI18n.Core/Capture/CaptureStore.cs:454-458` | `CaptureFilter.RejectReason` 命中即 `_filtered++` | 只有计数 |
| C# 运行时 | `src/UI18n.Core/Capture/CaptureStore.cs:464-482` | 模板档配额 `MaxTemplateEntries` 用尽 → `_templateSkipped++` | 只有计数 |
| C# 运行时 | `src/UI18n.Core/Capture/CaptureStore.cs:497-503` | 单 caller 配额 `MaxPerCaller` 用尽 → 不建记录 | 只有计数 |
| python 归并 | `tools/i18n_tools/capture_ingest.py:185-206` | 一串 `return ("never", reason)` 级联：empty / too-short / too-long / blank / logline / path / already-cjk / progress / counter / punct / identifier | 只进 `never` 计数 |

四个计数器在 1.4 的 `CaptureStore.cs:41-47`（`_filtered` / `_overflow` / `_templateSkipped` / `_never`）。**它们累加的是次数，不是文本。** v1.5 起前三个整体退役 —— `CaptureStore.cs:59-60` 写着「已退役（恒 0）」，属性只为外部调用点不炸而留着；现在剩下的两类计数都不再让正文消失：`_truncated`（超长只截断，`CaptureStore.cs:605-608`）与 `_never`（纯分桶分布，`:611-614`）。

**取证**：一局 4,040 条 distinct 里判 `never` 781 条、模板 3,179 条（[04 §3.7.2](04-翻译流水线与预处理.md)）；29 局去重 58,513 个 `h` 里 `never` **1,318** / `template` **56,632** / `candidate` **539**（root-cause §1.2）。这 1,318 条里没有一条能把原文捞回来看一眼 —— 「像噪声」是个**不可复核的判决**。

**后果**：判错即永久消失，系统里没有任何痕迹；下一轮只能等用户再报一次。

### 1.3 五条通道各自为政：没人答得出「还剩多少英文」

**机制**：cfg / loc / IL / ConfigCache / capture 五条通道各有去重键、过滤规则与分母，产物是五类不同的 jsonl。[reports/coverage.md](../reports/coverage.md) 开头就写着「三节口径互不相加」—— 这不是免责声明，是没有统一分母的直接后果。

**取证**：匹配层已经到顶 —— 对 29 局实测的 58,192 条原文逐层试，exact 命中 **14**（0.02%），skeleton 的 76 条全是 `#autoLOC_*` 噪声，剥符 / 分段 / 滑窗叠起来总共只值 **0.2%**（root-cause §1.1）。同一份会话重放出来的屏幕口径，最新的 [reports/screen-coverage.md](../reports/screen-coverage.md)（2026-10-26 13:16）是可译分母 3,129 里命中 **265** 条 = **8.47%**（exact 261 + pattern 4）；1.3 那张更早的快照只有 14 条 = 0.45%。8.47% 看着比 0.45% 好得多，但它和 17.54% 仍然不可比 —— 两者的分母一个是「事后重放推出来的可译集」，一个是「候选表里 distinct 行」。

**后果**：73.46%（pool 口径）、95.98%（IL 口径）、0.45%（屏幕口径）三个数字都「对」，但没有一个能回答玩家那句话：「这台机器上还剩多少英文？」

## 3. 数据流（v1.5 之后）

```text
                    ┌──────────── 预热（不再承担完备性）────────────┐
  cfg / loc / IL / ConfigCache 四条静态通道  ──┐                    │
                                              │                    │
 渲染出口（17 个 hook）── 未命中 ──► 捕获端 ────┼──► packs/candidates.jsonl ──► translate ──► packs/zh-cn/*.jsonl
                     │  只打优先级标签        │        （唯一候选清单）              │              │
                     │  正文一律留档          │                                       │              ▼
                     └── 命中/未命中计数 ──► render 覆盖率 ◄──────────────────────── 运行时查表
```

三条不变式：

1. **候选表的行数就是「已知但没翻」的上界** —— 静态与运行时都往同一张表里写。
2. **覆盖率只由运行时写** —— 静态工具不许自己造百分比。
3. **任何丢弃都必须留痕** —— 要么在表里留行（`never` 也是行），要么在日志里留一条计数。

## 5. 三个覆盖率数字，别混着用

### 5.1 口径对照

| 口径 | 分母 | 分子 | 谁在用 |
|---|---|---|---|
| **pool 覆盖率** | `packs/pool.jsonl` 的 12,792 行（抽取阶段已剔除 empty / already-cjk / search-tags / dup） | `h` 能被 `packs/zh-cn/*.jsonl` 精确命中的行 | [reports/coverage.md](../reports/coverage.md) ①；**v1.5 起不再是验收口径** |
| **屏幕覆盖率** | 重放 29 局捕获得到的可译分母 3,129 条（`screen_coverage` 的 applicable 口径，已排除 never 与运行时标注的 path / progress / counter / identifier） | 其中已出中文的条数 —— 当前 **265**（exact 261 + pattern 4）= **8.47%** | [reports/screen-coverage.md](../reports/screen-coverage.md)；1.3 起有，靠事后重放 capture 算，不是运行时自报 |
| **render 覆盖率**（v1.5 新） | **本会话**渲染过的 distinct 串（运行时自报的 `hit + miss`） | 其中命中译文的条数 | 启动日志 + `render-<stamp>.json`；**唯一对用户承诺的数字** |

三者不可相加、不可互相换算：pool 是「源侧待译串」，屏幕是「事后重放推算」，render 是「运行时自报」。

### 5.2 render 覆盖率怎么读

运行时在会话结束（或配置的采样点）打一行：

```text
[UI18n] render coverage: hit=<n> miss=<n> distinct=<n> ratio=<0.0000>
```

- `hit + miss` 未必等于 `distinct`：同一个串先 miss 后 hit（热加载 / 包更新）只算一条；
- `ratio = hit / distinct`，分母只统计「渲染出口真实交出、长度 ≥ 2 的 distinct 文本」；
- 明细落 `<KSP>/PluginData/UI18n/render-<UTC stamp>.json`，字段与读法见 §6.3。

### 5.3 报告口径

[reports/coverage.md](../reports/coverage.md) 必须同时列 **pool** 与 **render** 两个口径，并各带一句分母说明；屏幕覆盖率单列一节（它是重放口径，不是运行时口径）。**禁止**只写一个百分比就收工。现状：`coverage.md` 只有 pool 一节 + 屏幕一节；render 那一节要等第一次真会话落出 `render-*.json` 才能补（工具已就绪，§6.3），在那之前报告开头那句「三节口径互不相加」继续有效。

## 6. 验收清单

### 6.1 候选表

```powershell
cd tools
python -m i18n_tools.candidates --selftest        # 工具自检（schema / 排序 / covered 判定）
python -m i18n_tools.candidates                   # 默认就写 ../packs/candidates.jsonl + ../reports/candidates.md
python -m i18n_tools.candidates                   # 再跑一次
Get-FileHash ../packs/candidates.jsonl -Algorithm SHA256   # 两次必须同字节
```

**注意：这条命令没有 `--all` 参数**（`screen_coverage` 有，照抄那个写法会直接报 unrecognized arguments）。默认扫 `<KSP>/PluginData/UI18n/capture-*.jsonl`；要指定文件就 `--capture a.jsonl b.jsonl`，换目录就 `--capture-dir <dir>`，只并静态四条通道用 `--no-capture`（手机 / CI 上没有会话数据时用）。

确定性判据（D-T3）：**同输入两次运行 `sha256` 相同**；行序 = `bucket` 优先级 → `h`。

**本轮实测（2026-10-26 17:2x 快照）**：五条通道按 `h` 去重 **77,265** 行（同日已见 77,228 → 77,232 → 77,234 → 77,265 —— capture 通道随会话增长，**行数不是定值**）。报告的唯一分母是**可翻 71,359 行**（= 77,265 − keyref 3,187 − 占位符 2,719）：已覆盖 **13,522 = 18.94%**、未覆盖 57,837；全表口径 covered 13,544 = **17.53%**、未覆盖 63,721。产物 **25,888,054 B**、sha256 `88B54BC4F5E972A47472BF0BE51AD0666720E7F7D3F2BF42B3962F594FCDB0A0`；报告 **11,469 B / 10 节**。连跑两次逐字节相同（判据 ② 是「同输入两次同字节」）；重算命令 `cd tools` 后 `python -m i18n_tools.candidates`。单次约 10–11 s（大头是扫 dll 反查 `caller`）；`--selftest` **25 / 25**。

**同日二次实测补的三条口径**（都能在 `reports/candidates.md` 与源码里对上）：

1. **keyref 判据**：`harvest_cfgcache._KEYREF_RE`（`^#[A-Za-z0-9_]+$`）只覆盖下划线式；cfg 里真实还有 `#LOC.SXT_xxx` / `#LOC_Restock_variant-xxx` / `#Sol_Jupiter_name//Jupiter`，由本模块宽松式 `^#[^\s]+$` 兜住（`candidates.py:67-68`）。判据统一是「`#` 开头且不含空白」→ 命中行降 `bucket=never` + `reason=keyref` 并**踢出可翻分母**：本轮 **3,187 行**（其中已覆盖 22）。
2. **candidate 档未覆盖 488 条** = 下一批翻译的实际工作量，报告第 8 节专列这一档（按 channel/mod 分布）；capture×candidate 只剩 5 条未覆盖，il×candidate 与 cfg×candidate 占大头。
3. **可翻单位 1,226** = candidate 未覆盖 **488** + template 骨架 **729** + 塌不出骨架 **9**。template 可翻行经 `skeleton.py` 塌缩成骨架，另 9 条数字段为 0 或超过 8 个、塌不出骨架，出包时降级成 candidate 原样送翻；never 档留档、不送翻。

所以「还剩多少英文」不能按 57,837 条报数，也不能按 71,359 报；**工作量的正确单位是 1,226**。

### 6.2 golden set

每条 golden 原文必须同时满足三件事：① 捕获端判为「保留」（`bucket` ∈ candidate / template / never，且理由词里不含 drop / discard / overflow / lost / truncat）；② 在 `packs/candidates.jsonl` 里；③ 在 `packs/zh-cn/*.jsonl` 里有非空译文（`keep` 直通算过）。`h` 一律现算，不信任任何输入行里的 `h`。

### 6.5 联网更新从未真正生效：KSP 把 `//` 之后的值砍掉了（1.5.1 修）

第一次带着原值打出日志之后（KSP.log 17:19:41.697，v1.5.0 装机现场）：

```text
[WRN] [UI18n] update: disabled (invalid-url, UpdateBaseUrl="https:"), only https:// or http://127.0.0.1/localhost are accepted; nothing was requested
```

注意引号里是 `"https:"`，不是配置文件里写的那一整条 URL。**这不是判据写错，是值在读进来之前就没了。**

#### 6.5.1 根因：`ConfigNode.PreFormatConfig` 无条件截断

反编译 `KSP_x64_Data/Managed/Assembly-CSharp.dll` 的 `ConfigNode`：

- `ConfigNode.Parse(string s)`：`return RecurseFormat(PreFormatConfig(s.Split('\n', '\r')));`
- `private static List<string[]> PreFormatConfig(string[] cfgData)`：切行后对每一行执行

```csharp
if ((num2 = list[num].IndexOf("//")) != -1)
{
    if (num2 == 0) { list.RemoveAt(num); continue; }   // 整行注释
    list[num] = list[num].Remove(num2);                 // 行内注释：// 之后全砍
}
```

两个致命细节：

1. `IndexOf("//")` **无条件、不认引号**。所以 `UpdateBaseUrl = https://raw.githubusercontent.com/…` 在进入 ConfigNode 之前就变成 `UpdateBaseUrl = https:`。
2. **加引号救不了**：截断发生在引号处理之前，`"https://x"` 一样被砍成 `"https:`。

复现命令（本机）：`ilspycmd -t ConfigNode Assembly-CSharp.dll > %TEMP%\confignode.cs`，然后搜 `PreFormatConfig`。
这条规则对 KSP 生态里所有 cfg 都成立，也就是**任何 cfg 值里都不可能出现 `//`**——这一条以前没人写下来过。

#### 6.5.2 为什么之前几次「修」都没修到

- v1.2 起这条链路看起来是通的：manifest 拿得到、日志说 `up to date`。实际那些日志来自**手动**跑 `tools/publish-update.ps1`（它用 PowerShell 直接 GET），游戏进程从来没发出过请求。
- 诊断方向被日志误导：`invalid-url` 只说「判据不接受」，没说「值是什么」。所以先怀疑了 Mono 上的 `System.Uri.TryCreate`，并把 `UpdateUrlGate` 改成不依赖 `System.Uri` 的自解析（`src/UI18n.Core/Update/UpdateUrlGate.cs`，改动本身仍然有价值：少一个平台差异，且多一条 `ReasonScheme` / `ReasonHost` 的取值证据）。
- 真正定位靠的是**把被拒的原值打进日志**（`src/UI18n.Runtime/Update/UpdateWorkflow.cs` 的 Warn 里加 `UpdateBaseUrl="<value>"`）。一条日志里带上原值，比十条猜测有用。

#### 6.5.3 修法：URL 从原始文本补读

- 新增 `src/UI18n.Core/Config/ConfigText.cs`（`public static class ConfigText`）：`ReadValue(string path, string key)` / `ReadValueFromText(string text, string key)`。逐行扫第一个 `键 = 值`，跳过整行 `//` 注释，剥成对双引号，**不对值里的 `//` 做任何处理**（那正是要保留的东西）。
- `src/UI18n.Runtime/ConfigLoader.cs` 在读完 `UpdateBaseUrl` 之后判「残值」（以 `:` 结尾且不含 `/`，即 `https:` / `http:`），命中就用 `ConfigText` 从原文补读，并打一行 `Log.Info` 说明被谁截断、补读到了什么；补读失败则 Warn 提示「把 URL 独占一行」。
- `GameData/UI18n/Config.cfg` 的注释里写明：**KSP 会砍掉 `//` 之后的一切，URL 必须独占一行，别在同一行写注释**；也解释了为什么不能用行尾注释来「顺便说明」。
- 单测 `tests/UI18n.Core.Tests/ConfigTextTests.cs`（10 例）钉住：完整 https 值、带引号、注释行、缺键、大小写不匹配、CRLF + 缩进、行内 `//` 原样保留、空值、文件读不到。
- 这一层只兜住**我们自己的** cfg。第三方 mod 的 cfg 里若有 URL 类值，作者早就踩过同一个坑（多半用 `https:example.com/x` 这种畸形写法或干脆拆成多键），我们不替他们改。
