# 05 · 原生性与性能调研：到底需不需要 hook

> 争议起点（用户 m00615 原文）：**"调研性能问题，居然不是做到原生UI显示吗？需要进行hook？"**
>
> 一句话回答：**A/B 两类文本本来就该走原生、零 hook，当前设计已经如此；hook 只为 C 类（DLL 里的硬编码字面量）存在。** 另外要纠正一个前提——**原生 ≠ 零成本**，KSP 自己的本地化也是每次绘制时查表（实测全 GameData 有 3,434 个 Localizer 调用点）。

---

## 0. 结论摘要

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 能不能不 hook，全做原生？ | **八成的文本可以**（cfg 9,844 + Localization 2,948 = 12,792 条零 hook） | 04 文档 §3 语料统计 |
| 剩下两成必须 hook 吗？ | **必须**。硬编码在 IL 里的字符串没有数据通道，MM 碰不到 | 本文 §3 实测 |
| hook 会不会拖帧？ | **不会**。单次 17–21 ns，最坏 3,000 次/帧也只有 51 µs（0.31% 帧） | 本文 §4、§5 |
| 真正的性能风险是什么？ | 不是查表，是①每帧 new GUIContent ②误拦引擎级漏斗导致全游戏过一遍 | 本文 §6 |
| 有没有完全原生的替代方案？ | 有：IL 改写（把 ldstr 换成 key）。但代价高于收益，列为实验分支 | 本文 §7 |

## 1. 先拆问题："原生 UI 显示"在 KSP 里指什么

用户质疑的其实混了两件事，必须分开：

**① 显示层面**：中文是不是由游戏自己画出来的？

**② 成本层面**：翻译这件事发生在加载期一次，还是绘制期每帧？

### 1.1 显示层面：我们的方案本来就是原生绘制

关键在**拦截点选在哪里**。三种位置，效果完全不同：

| 拦截位置 | 谁去排版中文 | 结果 |
| --- | --- | --- |
| 绘制**之后**（往屏幕上补画中文/贴图） | 没人，英文先排好版 | 布局按英文宽度算，中文溢出、截断、按钮尺寸错 |
| 绘制**之中**（改 GUI 状态、改 skin） | Unity | 可行但极脆弱，且只能改样式不能改内容 |
| **控件拿到文本之前**（setter / 分流漏斗） | Unity 用中文重新排版 | **与原生完全一致**，没有覆盖层、没有事后替换 |

本设计走的是第三种：在 `Text.set_text` / `GUILayout.DoLabel` 这些「文本进入控件的入口」把字符串换掉，**控件随后拿到的是中文**，它自己去测宽、换行、算 Rect。所以显示效果和 Squad 自己做的中文本地化没有区别——不是外挂式翻译，是**在入口处换掉内容**。

结论：**"原生 UI 显示"这一点，当前设计已经满足**，不存在"补画中文"的问题。

### 1.2 成本层面：原生也不是零成本

KSP 自己的 `KSP.Localization.Localizer.Format` 就是一个运行时查表函数。全 GameData 实测：

| 项 | 实测值 |
| --- | --- |
| 调用 `Localizer.Format/GetString/GetStringByTag` 的 IL 调用点 | **3,434 处** |
| 分布在这条原生路径上的程序集 | 大部分已支持 i18n 的 mod |
| 同一方法里既有渲染 sink 又有 Localizer 调用的站点 | **1,436 处（占全部渲染站点的 23.1%）** |

也就是说：**支持 i18n 的 mod，本来就在每次 OnGUI 里逐条调 `Localizer.Format` 查表。** 我们 hook 做的事（一次 FNV 哈希 + 一次字典查表）与它同量级甚至更便宜（原生路径要走 ConfigNode → 字符串字典 → Format 占位符替换）。

所以"原生 = 免费"这个直觉在 KSP 里不成立。真正该问的不是"要不要查表"，而是"**查多少次、每条多少 ns、会不会分配内存**"——这是 §4/§5 回答的。

### 1.3 显示的第二个前提：字体里有字形（与 hook 同级的必做项）

v0.2 之前，字体层（L3）被当成"收尾阶段再补"的收尾项。**这个判断是错的**，本轮把它提到与 hook **同级**的必做项：

- 文本翻对了、patch 也命中了，只要字体里没有汉字字形，玩家看到的是 一 片 方 框。**命中率再高也救不回来**；
- 反过来，字体通了、patch 一条没装上，至少 mod 自带中文能显示。**这两层的失败模式不对称**：字体是"全盘可读性"，hook 只是"覆盖率"。

本机实测（2026-10-23，遍历 `GameData` 全部 `*.ttf/*.otf/*.ttc`）：

| 项 | 实测 |
|---|---|
| GameData 下字体文件总数 | **13 个**（全部在 `ConformalDecals/Fonts/`） |
| 字族 | 5 个：Carlito / Gyrotrope / League Spartan / Neuropol / Nimbus Sans |
| 含 CJK 字形的字体 | **0 个** |

KSP 本体中文字体打在 `KSP_x64_Data` 的 asset bundle 里，**取不出来**；也不做系统字体探测（D33，理由见 00 §3.4 与 00 §12 Q-G）。所以结论只有一条：**必须随包带一份 OFL 中文字体子集**。

当前实现状态（不许谎报）：`src/UI18n.Runtime/Fonts/FontProbe.cs` **只探测、不注入** —— 它用 `Resources.FindObjectsOfTypeAll<TMP_FontAsset>()` / `<Font>()` 数一遍已加载字体里有没有 中/推/。 三个样本字，日志 `font probe: …`；没有 CJK 时打 `Log.Warn("font probe: no CJK glyphs found in loaded faces; Chinese text may show as □□□ (UI18n does not inject fonts — install a CJK font pack yourself)")`。全仓 grep `FontMode` / `CreateDynamicFontFromOSFont` / `fallbackFontAssetTable` 命中 **0** → 注入层是**待做**，规范写在 00 §3.4（`FontMode = Off | OsFont | Bundled`、懒加载、降级行为）。

## 2. 三条文本通道：谁需要 hook

| 通道 | 文本来源 | 数量 | 注入方式 | 需要 hook？ |
| --- | --- | --- | --- | --- |
| **A 类** | cfg 里的 `title / description / displayName / tags` | 9,844 条 | MM 在加载期把字面量键化（改成 `#uii18n_xxx`）+ 注入 Localization 节点 | **不需要** |
| **B 类** | mod 自带的 `Localization/*.cfg` 里的 key | 2,948 条 | MM 往同一个 Localization 节点补 `zh-cn` 子节点 | **不需要** |
| **C 类** | DLL 里硬编码的字符串字面量（`ldstr`） | 见 §3 | 没有数据通道，MM 加载后才存在的 ConfigNode 空间里根本没有它们 | **必须** |

**A/B 两类是"真原生"**：键化发生在 GameDatabase 加载期，之后游戏走的是 Squad 自己的 `Localizer.Format` 路径，切语言、存档、其他 mod 读 `title` 全都正常。这条路径零 hook、零每帧成本。

这也解释了为什么 RP1GUIZh 那种"整包 hook"是错的：它连 A/B 类文本都用 hook 去改，白白把加载期能做好的事搬到每帧。

**C 类为什么没有数据通道？** 因为字符串是编译进 IL 的常量，例如 `GUILayout.Label("Switch to Hangar")`。它在程序集里是一段 UTF-16 数据，KSP 的 ConfigNode 体系根本不认识它。要在不修改 DLL 的前提下影响它，只有运行时拦截这一条路（另一条路是 IL 改写，§7 讨论）。

## 3. C 类到底有多大：Cecil 全量扫描实测

### 3.1 方法

用 Mono.Cecil 扫描 GameData 下全部托管 DLL（就是 KSP 自带的那份 `Mono.Cecil 0.9.6`），对每个方法体：

1. 找出所有指向**渲染 sink** 的 `call/callvirt` 指令；
2. 统计同方法体内的全部 `ldstr` 字面量（上界估计：方法里出现的字面量都可能流向该 sink）；
3. 记录该方法是否也调用了 `Localizer`（判断该 mod 是否已支持 i18n）。

### 3.2 总量

| 指标 | 值 |
| --- | --- |
| 成功扫描的托管程序集 | **128**（`principia.dll` 是混合模式，Cecil 读不了，计 2 次失败） |
| 渲染 sink 的 IL 调用点 | **6,221** |
| 含渲染 sink 的方法 | **1,216** |
| 这些方法里的字面量（去重） | **6,290** |
| 全量字面量（对照） | 88,384 |
| Localizer 调用点 | 3,434 |

### 3.3 6,290 条字面量里，真正要翻的有多少

| 分类 | 条数 | 说明 |
| --- | --- | --- |
| 已在语料池里（A/B 类可达） | 92 | 不该重复翻，查池即可 |
| `#` 开头的 key | 1,258 | 本身就是本地化 key，交给原生 |
| 已含中文 | 542 | 作者自己写死的，跳过 |
| 长度 <3 或纯符号 | 292 | 噪声 |
| 标识符类（`pitch`、`GUI.Button`…） | 1,674 | 不是 UI 文本 |
| **散文候选（钩子才碰得到的真·缺口）** | **2,432** | 例如 "Load Pattern"、"Universal IMGUI click-through blocking" |

**所以 C 类真缺口的量级是 2 千条上下，不是 12 万条。** 这也是为什么"hook"不等于"把整个游戏的字符串都拦一遍"。

### 3.4 但 hook 的**面**比想象的小得多

6,221 个调用点，按 sink 类型分布：

| sink | 调用点 | 运行时特性 |
| --- | --- | --- |
| `GUILayout.Label` | 3,057 | IMGUI，每帧 ×2 pass |
| `GUILayout.Button` | 1,221 | 同上 |
| `GUILayout.Toggle` | 459 | 同上 |
| `GUILayout.TextField` | 323 | 输入框，**不采** |
| `UnityEngine.UI.Text.set_text` | 293 | uGUI，**事件驱动**，改文本才触发 |
| `GUI.Label` | 185 | IMGUI |
| `GUI.Button` | 174 | IMGUI |
| `TMPro.TMP_Text.set_text` | 174 | 事件驱动 |
| `GUILayout.TextArea` | 75 | 输入框，**不采** |
| `GUILayout.Window` | 64 | IMGUI |
| 其余（Box/TextField/Window/Toggle） | 347 | — |

关键：**IMGUI 的 5,304 个调用点在运行时全部收敛到 4 个私有静态方法**——`GUILayout.DoLabel`、`DoButton`、`DoToggle`、`DoWindow`（02 文档 §4.3 已用 ilspycmd 核实签名）。所以 hook 的面不是 6,221 个调用点，而是十来个方法。

#### 3.4.1 hook 面定稿：16 个目标（v0.3，逐条对着实现数出来）

v0.2 记的「12 个方法」是估算（4 个 IMGUI 漏斗 + 2 个 setter + 6 个 GUI 重载）。定稿是 **16 个**，与 `src/UI18n.Runtime/Patches/PatchRegistry.cs:25` 的 `internal const int ExpectedPatchCount = 16;` 一一对应：

| # | 目标 | 文本参数 | 备注 |
|---|---|---|---|
| 1 | `UnityEngine.UI.Text.set_text(string value)` | #0 | uGUI，事件驱动 |
| 2 | `TMPro.TMP_Text.set_text(string value)` | #0 | **必须打声明方法**，不是 `TextMeshProUGUI` 的属性访问器（01 §4 的事故） |
| 3 | `GUILayout.DoLabel(GUIContent, GUIStyle, GUILayoutOption[])` | #0 | 3,057 个 Label 站点的漏斗 |
| 4 | `GUILayout.DoButton(GUIContent, GUIStyle, GUILayoutOption[])` | #0 | 返回 bool |
| 5 | `GUILayout.DoRepeatButton(GUIContent, GUIStyle, GUILayoutOption[])` | #0 | 返回 bool |
| 6 | `GUILayout.DoToggle(bool, GUIContent, GUIStyle, GUILayoutOption[])` | #1 | 文本在 #1，不在 #0 |
| 7 | `GUILayout.DoWindow(int, Rect, GUI.WindowFunction, GUIContent, GUIStyle, GUILayoutOption[])` | #3 | `GUILayout.Window(string)` 直连它 |
| 8 | `GUI.Label(Rect, GUIContent, GUIStyle)` | #1 | |
| 9 | `GUI.Box(Rect, GUIContent, GUIStyle)` | #1 | |
| 10 | `GUI.Button(Rect, GUIContent, GUIStyle)` | #1 | |
| 11 | `GUI.Toggle(Rect, bool, GUIContent, GUIStyle)` | #2 | |
| 12 | `GUI.Toggle(Rect, int, bool, GUIContent, GUIStyle)` | #3 | 带 controlID 的重载，文本在 #3 |
| 13 | `GUI.RepeatButton(Rect, GUIContent, GUIStyle)` | #1 | |
| 14 | `GUI.DoWindow(int, Rect, GUI.WindowFunction, GUIContent title, GUIStyle, GUISkin, bool)` | #3 | **private 漏斗** |
| 15 | `GUI.DoModalWindow(int, Rect, GUI.WindowFunction, GUIContent content, GUIStyle, GUISkin)` | #3 | **private 漏斗**，参数名是 `content` 不是 `title` |
| 16 | `ScreenMessages.PostMessage(ScreenMessage, string msg, …)` | #1 | 唯一改 `string` 实参的目标 |

四条把这个表面定死的实测结论：

1. **`GUILayout.DoBox` 撤掉**（T5b2）。反编译实测它的方法体只有一句转发：`GUI.Box(GUILayoutUtility.GetRect(content, style), content, style)` —— 打它只多一次**必然 miss** 的查表，而 `GUI.Box` 已在第 9 条里。`GUILayout.Box(string)` 经它转发到 `GUI.Box`，覆盖不受影响。
2. **必须打两个 private 漏斗**。`GUILayout.Window(string)` 的实现是 `return DoWindow(id, clientRect, func, GUIContent.Temp(text), skin.window, skin, forceRectOnLayout: true);` —— 它**绕过**公开的 `Window(GUIContent title, GUIStyle)` 直连 `DoWindow`；`ModalWindow(string)` 同理直连 `DoModalWindow`。只打公开重载会漏掉**所有** `Window(…, string)` 调用。
3. **参数名守卫是硬性的**。Harmony 是按**参数名**把 prefix 的 `ref` 绑到目标参数的：名字不对**不抛异常、只静默失效**。所以注册表对每个目标核对参数名，不符就 `Log.Error("patch failed: " + spec.Target + " → prefix parameter name mismatch: " + mismatch)`，最后打印 `installed N/16 patches`。第 14 条叫 `title`、第 15 条叫 `content`，两者不能共用同一个前缀方法。
4. **屏幕消息是唯一改 `string` 的目标**。它的签名里根本没有 `GUIContent`，所以 `ScreenMessagesPatches.MessagePrefix(ref string msg)` 改的是传进来的字符串实参，不碰 `ScreenMessage` 实例、不碰 `ScreenMessages` 的静态状态 —— 这是 C1 允许的唯一例外形态（00 §3.3）。

12 → 16 的差额来自四件事：撤掉 DoBox、补上 `GUI.RepeatButton`、补上两个 private 漏斗、补上 `ScreenMessages`。**这个清单是白名单**（00 §8.2 C3）：CI 构建期生成实际 patch 清单与它比对，多一条少一条都 fail。

## 4. 性能实测

### 4.1 测量环境（重要，见 §9 局限）

| 项 | 值 |
| --- | --- |
| 运行时 | .NET Framework 4.7.2（CLR 4.x，x64） |
| Harmony | KSP 自带的 **0Harmony 2.2.1.0**（直接引用 GameData 里那个 dll） |
| 方法 | 200 万次调用取 3 轮最小值；含 warmup |
| 为什么不是 Mono | KSP 用 Unity 2019.4 的 **Mono + Boehm GC**（`mscorlib 4.6.57.0`，`mono-2.0-bdwgc.dll`）。Harmony 2.2 的 detour 在本机 .NET 10 上会触发 `Internal CLR error 0x80131506`（MonoMod PrepareMethod），只能用 CLR 4.x 近似 |

### 4.2 结果

| # | 场景 | ns/call | 相对基线 |
| --- | --- | --- | --- |
| A | 未拦截（基线，静态方法） | 2.6 | — |
| A2 | 未拦截（基线，属性 setter） | 2.6 | — |
| B | Harmony + **空 Prefix**（立即 return） | 2.8 | **+0.2** |
| C | Harmony + FNV + 查表，**未命中** | **17.1** | +14.5 |
| D | Harmony + 哈希 + **命中并改写** | **20.6** | +18.0 |
| E | 同 C 但不经 Harmony（纯函数） | 18.9 | +16.3 |
| F | Harmony + 属性 setter 拦截 | 19.6 | +17.0 |
| G | `new StackTrace(2,false)` 抓调用者 | **2,072.9** | ×797 |
| H | 100 万次未命中调用的内存增量 | **0 B**（GC0 次数 1） | — |
| I | 仅 FNV-1a，23 字符 | 10.7 | — |
| J | 仅 FNV-1a，100 字符 | 65.7 | — |
| K | `Dictionary<ulong,string>` 未命中 | 4.5 | — |
| L | `Dictionary<string,string>` 未命中 | 10.6 | — |

### 4.3 五条可以直接落到设计上的结论

**① Harmony 的调度开销可以忽略（+0.2 ns）。** 成本全在我们自己的前缀里。此前担心的"每帧 3,000 次经过 detour 会拖慢"不成立。

**② 未命中 17.1 ns、命中改写 20.6 ns。** 这两个数字是**整个项目的性能天花板**，比 00 文档 §9 原来拍的"命中 <50ns / 未命中 <15ns"更真实——命中达标且更好，未命中略超（17.1 vs 15），建议把预算改成 **未命中 <25 ns、命中 <35 ns**，给 Mono 留 1.5× 余量。

**③ 哈希是主要成本，且随长度线性增长（I/J）。** 23 字符 10.7 ns，100 字符 65.7 ns ≈ 0.66 ns/字符。这意味着：**长文本（部件描述 200+ 字符）直接哈希会到 130 ns**。设计必须加**长度闸门**：超过阈值的字符串先用"长度 + 首尾 8 字符"做前缀判据，只有可能命中时才做全量哈希。

**④ 预计算哈希键值钱（K vs L）。** `Dictionary<ulong,string>` 4.5 ns，而 `Dictionary<string,string>` 10.6 ns —— 2.4 倍差距。这印证了 02 文档 §5.1 选 FNV-1a 64 位整数键而不是字符串键的决定。

**⑤ 抓调用栈贵 100 倍（G）。** 2,073 ns 相当于 100 次正常查表。归因必须严格"首见串才抓一次"，且全局预算 4,000 次（02 文档 §6）是合理的——最坏 4,000 × 2 µs = 8 ms，一次性成本。

**⑥ 零分配可达（H）。** 100 万次未命中，内存增量 0 字节。这一条在 KSP 上比在 .NET 上更重要：KSP 用 **Boehm GC**（非分代、保守式），分配压力直接变成卡顿。

## 5. 每帧预算推算

一帧 60 fps = 16.67 ms = 16,666,667 ns。

| 场景 | 每帧 sink 调用 | ×20 ns | 占帧 |
| --- | --- | --- | --- |
| 空闲（KSC 主界面） | < 100 | < 2 µs | 0.01% |
| 典型（开一个 MechJeb 面板） | 200–600 | 4–12 µs | 0.02–0.07% |
| 极端（多个 IMGUI 窗口全开） | ~3,000 | ~60 µs | **0.36%** |

注意 IMGUI 的 `OnGUI` 每帧至少跑两次（Layout + Repaint），上面的数字已经把 ×2 算进去了。而 uGUI / TMP 那 467 个站点是**事件驱动**的（改文本才触发），稳态几乎为零。

**结论：hook 不是性能风险源。** 一个 IMGUI 窗口自己画一帧（字宽测量 + 图集查字形 + 生成网格）就是几十到几百微秒，我们插在它入口的 20 ns 连零头都算不上。

## 6. 真正的性能风险：两处，都不在查表

### 6.1 每帧 new GUIContent（必须解决）

02 文档 §4.3 已确认：`GUIContent.Temp()` 返回的是 Unity **内部共享缓存实例**，原地写 `content.text` 会把译文永久写进全游戏共用的对象（RP1GUIZh 就踩了这个坑）。所以命中路径必须**构造新的 GUIContent**。

一次分配 ≈ 40 字节。粗算：600 次命中 × 2 pass × 60 fps × 40 B ≈ **2.9 MB/s**，在 Boehm GC 上是实打实的卡顿来源。

**解法**：命中路径缓存的不是字符串，而是**翻译后的 GUIContent 实例**——

~~~
Dictionary<ulong, Entry> dict;
struct Entry { public string Src; public string Dst; public GUIContent Gc; }
~~~

稳态下同一个源串每帧重复出现，命中后直接复用已有 `GUIContent`，**零分配**。代价是命中路径多一次引用比较（忽略不计）。这一条要写进实现约束。

### 6.2 误拦引擎级漏斗（必须约束）

`GUI.Label` / `GUILayout.DoLabel` 是 Unity **引擎级**漏斗——不只被 mod 用，KSP 自己也用。拦了它等于让全游戏每一处 IMGUI 文本都过一遍我们的前缀。即使每次只有 17 ns，也要保证：

- 语言不是中文时**完全不装 patch**（不是装了就返回）；
- 命中率为 0 的帧要能自动降级（连查表都不做，用一个全局 `bool HasAnyTranslation` 短路）；
- 绝不在前缀里调用任何游戏 API（02 文档 §2 红线）。

## 7. 如果坚持"完全原生"：IL 改写方案评估

唯一能把 C 类也变成"零运行时开销"的办法是：**在程序集加载前用 Cecil 把所有 `ldstr` 改写成 `Localizer.Format("#uii18n_xxx")`**，然后把 DLL 写回磁盘。这样游戏跑的是被改过的代码，运行时一点开销都没有。

| 维度 | IL 改写 | 运行时 hook（本设计） |
| --- | --- | --- |
| 运行时开销 | **0** | 17–21 ns/次 |
| 是否改第三方文件 | **是**（写回 GameData） | 否 |
| mod 更新后 | 补丁丢失，需重跑；CKAN 校验和失效 | 自动跟随 |
| 反射/序列化污染 | **会坏**：字符串若被 `GetField("name")`、`Resources.Load`、字典键、`Animator` 状态名使用，改了字面量就坏功能 | 无影响（只改 UI 入参） |
| 无法处理的目标 | 混合模式 dll（`principia.dll` 实测 Cecil 直接报 `BadImageFormatException`）、Assembly-CSharp（Squad 本体） | 无 |
| 可回滚性 | 需备份原 dll，回滚麻烦 | 卸载 mod 即恢复 |
| 失败模式 | 静默改坏玩法（最坏） | 翻不出来就显示原文（最坏也只是没翻译） |

**判定：不做主路径，列为实验分支 B16。** 理由不是做不到，而是**失败模式不可接受**——8,000 条字面量里只要有一条被反射用作资源名，玩家就会遇到"某个部件加载不出来"这种无从排查的 bug。而 hook 的最坏情况只是"这句还是英文"。

另一个折中值得一提：**只对确认安全的程序集做 IL 改写**（例如纯 IMGUI、无反射字符串用途的 mod），作为"性能增强包"可选启用。这个方向记入 B16，不进 M0–M5。

## 9. 局限与换算

1. **不是 Mono 实测。** .NET Framework 4.7.2 的 JIT 通常优于 Mono 5.x；KSP 实际运行在 Mono + Boehm GC 上，保守估计各项慢 **1.5–3×**。所以预算按 1.5× 给余量（D26 相关论证仍成立，因为量级差是 100 倍级）。
2. **Harmony 版本差异。** 实测用的是 KSP 自带的 0Harmony 2.2.1.0，与实际一致；但 .NET 10 上无法运行（MonoMod 的 `PrepareMethod` 触发 CLR 内部错误），所以只能在 CLR 4.x 测。
3. **调用点 ≠ 调用次数。** 6,221 是静态站点数，每帧实际调用次数取决于开了哪些窗口、玩家长时间停留哪个界面。§5 的每帧估算基于站点密度推算，真实值要等 P1 探针实测（02 文档 §7 的 timing 字段）。
4. **2,432 条散文候选是上界。** 方法内出现字面量 ≠ 一定流向 sink，仍有 20–40% 会掉出去。真实缺口要等探针的运行时数据。
5. **GUI 渲染成本未实测。** §5 里"一个 IMGUI 窗口一帧几十到几百 µs"是量级估计，不是本机实测（需要跑起 KSP 才能测）。
