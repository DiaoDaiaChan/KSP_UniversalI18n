## 0. 本文解决什么

用户拍板了两件事（m00421）：**用这个 API 做翻译**、**把预处理做扎实**。所以本文的重心不是"怎么调 API"（那是最简单的一步），而是**送进去之前要做什么**和**出来之后要验什么**。

一句话立场：**LLM 的翻译质量基本够用，项目真正的风险全在预处理和校验上。** 实测已经证明了三件事：

1. 模型对占位符、富文本标签、URL 的保留能力**很好**（10 条折磨测试里 8 条完全正确）。
2. 模型对**路径、转义序列**这类"看起来像代码"的片段会犹豫甚至整条跳过。
3. 模型**没有跨批次记忆**——同一个词换个批次就换一种译法。这不是模型不行，是架构上必须由我们补的。

第 3 条是全部设计的出发点：**术语一致性不可能靠 prompt 保证，只能靠"锁定 + 缓存 + 复核"三道工序保证。**

## 1. API 实测结论

### 1.1 基本参数

| 项 | 值 |
|---|---|
| Base URL | `http://100.111.24.121:8317/v1` |
| 认证 | `Authorization: Bearer <token>`（token 见 §13，**不入库**） |
| 模型 | `gemini-3.8-flash-high` |
| 可用模型 | 35 个，含 `gemini-3.8-flash` / `gemini-3.8-flash-high` / `gpt-6-*` / `claude-opus-4-6-thinking` / `kimi-k3` / `glm-5.3` / `grok-4.7` |
| 响应结构 | `choices[0].message = {role, content, reasoning_content, tool_calls}` |
| 用量字段 | `usage.prompt_tokens / completion_tokens / completion_tokens_details.reasoning_tokens` |

### 1.2 实测性能（同一 system prompt + 真实航天术语）

| 场景 | 耗时 | prompt tok | completion tok | 其中 reasoning | 结果 |
|---|---|---|---|---|---|
| 8 条 | 5.8 s | 376 | 521 | 426 | 全部正确 |
| 50 条（默认思考） | 10.4 s | 768 | 1,387 | 837 | 全部正确 |
| 50 条（`reasoning_effort: none`） | 5.5 s | 768 | 553 | 0 | 全部正确 |
| **200 条**（none） | 17.4 s | 3,152 | 2,948 | 0 | 200/200 解析成功，`finish=stop` |
| 并发 4×50（none） | 7.7 s 墙钟 | — | — | — | 4/4 完整解析 |

**三个直接结论**：

- `reasoning_effort: "none"` 让 completion tokens 从 1,387 降到 553（**降 60%**），延迟减半，译文质量肉眼无差。批量翻译**默认关闭思考**。
- 200 条一批是安全的（没有截断、没有丢条）。批量越大，system prompt 的固定开销摊得越薄。
- 并发 4 可用，串行 24 s 的场景 7.7 s 跑完。

### 1.3 参数陷阱

| 参数 | 实测行为 | 结论 |
|---|---|---|
| `max_tokens` | **不被强制执行**：`max_tokens=20` + 开思考时仍返回完整内容，reasoning 占 282 tokens | 不要靠它控截断；靠批大小 + 检查 `finish_reason` |
| `response_format: {type:"json_object"}` | 被接受，但无可测收益 | 留着当保险，不依赖 |
| `temperature` | 0.2 稳定 | 用 0.2，不要更高 |
| 不指定输出 schema | 模型会自作主张包成 `{"translation": "..."}` | **schema 必须每次写进 prompt** |
| markdown 围栏 | 三种模式都没出现 | 但仍要容错剥壳 |

### 1.4 保留能力（成功案例）

实测 10 条"折磨"文本，以下元素**全部原样保留**：

| 元素 | 原文 | 译文 |
|---|---|---|
| KSP 占位符 | `Apoapsis: <<1>> m (<<2>>)` | `远拱点：<<1>> m (<<2>>)` |
| 格式占位符 | `{0} units of Liquid Fuel remaining` | `剩余 {0} 单位液体燃料` |
| printf | `Cannot activate %s while in atmosphere` | `在大气层内无法激活 %s` |
| TMP 富文本 + 色值 | `<color=#FF8000><b>Warning:</b></color> Overheat` | `<color=#FF8000><b>警告：</b></color>过热` |
| URL | `See https://github.com/KSP-RO/RealFuels for details` | `详情见 https://github.com/KSP-RO/RealFuels` |
| 侧化 key | `#autoLOC_6001234` | 原样 |
| 单位 | `Δv 3200 m/s` | 原样 |
| 缩写 + 数字 | `Stage 3 (SRB) — TWR 1.42` | `第 3 级 (SRB) — 推重比 1.42` |

### 1.5 失败案例（必须由预处理解决）

**① 含转义序列的整条被跳过。**

    输入: Line one\nLine two        （字面反斜杠 + n）
    输出: Line one\nLine two        （整条未译）

模型把它当成代码了。

**② 含文件路径的只译了一半。**

    输入: Config: GameData/RealFuels/Resources.cfg
    输出: Config: GameData/RealFuels/Resources.cfg   （Config: 未译）

**③ 术语漂移（最严重）。**

同一批词在不同批次跑出不同译法：

| 原文 | 批次 A | 批次 B | 批次 C |
|---|---|---|---|
| Apoapsis | 远地点 | 远拱点 | — |
| Activate Engine | 激活发动机 | 启动发动机 | — |
| Balloon Tank | 气球储罐 | 气球贮箱 | 气球储箱 |
| Avionics Package | 航电包 | 航电设备组 | 航电设备包 |

三个译法都能看懂，但玩家在界面上看到同一个东西叫三种名字，就是质量事故。**这是预处理必须解决的第一优先级问题。**

**源一：Localization 差集。**

### 3.4 键引用行：补解析行 + 删掉键行（v0.5 定稿，策略反转过一次）

harvest 从 IL 取到的是**字符串字面量**，而 mod 代码里写的常常是 `#autoLOC_500832` 这类**键**：

```text
mod 源码（IL 里的 ldstr）   →  #autoLOC_500832
运行时 KSP.Localizer 解析    →  "Found lying by the side of the road"（或中文）
送进 UI（我们的钩子看到的）   →  已经解析好的显示文本，不是键
```

所以池里文本**以 `#` 开头的行，在正常安装里几乎永远匹配不到** —— 钩子拿到的是解析后的文本。
实测规模：pool 12,792 行里以 `#` 开头 **3,193 行**（`#autoLOC_` 前缀 1,232，其余 1,961 是 mod 自有键
`#LOC_*` / `#Sol_*` / `#MechJeb_*` 等）；1,232 条 autoLOC 里 **993 条**能在官方译文记忆里查到中文、239 条查不到。

**这是采集阶段的结构性限制，不是 bug**：harvest 离线跑在 IL 上，没有游戏上下文、也不知道玩家当前语言，
拿不到「KSP 解析之后」的文本。修复层只能放在后处理。

#### 3.4.1 四步流水线（顺序不能颠倒）

后处理是 `tools/i18n_tools/resolve_keyrefs.py`，**常驻步骤**，必须跟在 `translate --keyref-rescue` 后面跑
（① 会整文件重写 `packs/zh-cn/*.jsonl`，把后面三步的结果冲掉）：

| 步 | 命令 | 做什么 | 本轮（2026-10-23 08:31:54） |
|---|---|---|---|
| ① | `translate --keyref-rescue` | 翻译并整文件重写 packs | 写盘 10,043 行 |
| ② | `resolve_keyrefs`（补行） | **只追加**键引用解析行 | +917 |
| ③ | `--prefer-official` | 已有行里 `s` 与官方 `en` 逐字节相同、官方 `zh` 过门禁的，把 `t` 覆盖成官方值 | 1 条 |
| ④ | `--drop-keyrefs` | **删除** `s` 以 `#` 开头的键引用行（守卫拦下的 22 条保留，见 §3.4.4） | −970 |

②③④ 是**同一个命令的三个开关**、默认全开，所以正常只跑一条 `python -m i18n_tools.resolve_keyrefs`；
单独跑 ③ 或 ④ 是幂等空操作（`official_overrides = 0` / `dropped = 0`，字节不变）。
关闭开关：`--no-prefer-official` / `--no-drop-keyrefs`。

**② 补解析行（只增不改）**：

- `s = glossary.en`（官方英文原文）、`t = 官方中文`、`n = normalize(s)`、`h = hash_text(n)`、`mod`/`ctx` 沿用原键引用行；
- 补行前逐条过门禁（与 Lead 侧 `_scratch/audit_packs.py` 的 tag_re 逐字节同口径）：占位符 `<<n>>` 多重集、
  TMP 标签多重集、`{n}`/`%s` 多重集、`t != s`、`t` 非空；
- 本轮：键引用行 992 → 新增解析行 **917**；`existing 29`（该英文串的 `h` 已在包里，按「不改行」原则跳过）/
  `duplicate 24`（同一英文串由多个键指向，只补一次）/ `ambiguous_skipped 14`（歧义守卫，见 §3.5）/
  `gated_ratio 8`（长度比门禁，见 §3.5）/ `unresolvable 0` / `gated 0`；行数 10,043 → **10,960**；
  本步结束时 `s#` 仍是 992（本步只增不减，清理由 ④ 负责）；
- **核对等式**：`992 = 917 + 29 + 24 + 14 + 8`。五项之和必须等于键引用行总数 —— 不等就是插入侧漏了分支。

#### 3.4.2 为什么把键行删掉（v0.5 策略反转，这是决策依据）

1. **零覆盖价值**：被删的 970 条，其官方英文+中文**已经全部以解析行或已有行形式存在于包里**
   （覆盖证明逐条验证，见 §3.4.3）——键行只是同一份译文的第二份副本。
2. **纯体积**：970 行 = **191,486 字节（187.0 KiB）**，占删前包体 **5.18%**（3,695,878 B）；
   其中 Squad 独占 **959 行**（`Squad.jsonl` 1,889 → **930 行 / 360,369 B**）。
3. **删了不影响命中**：键行唯一可能命中的场景是「某个 mod 把未解析的键直接塞进 GUI」，而那时它给出的译文
   与解析行**完全一样** —— 它不是后备，是冗余。

#### 3.4.3 零覆盖损失硬门禁与实测

删除前对**每一条**待删行验证其官方中文 `zh` 必须能在剩余行里找到；任一条不满足就**整体放弃、一个文件都不写**
（CLI 返回码 2）：

| 类别 | 判据 | 本轮 |
|---|---|---|
| ① 同文件 | 同一文件的剩余行里有某行 `t == zh` | 941 |
| ② 全局 | 全局剩余行里有某行 `t == zh` | 29 |
| ③ en 等价 | 全局剩余行里有某行 `s == glossary.en`（逐字节） | 0 |

第 ③ 类的理由：`DictPack` 以 `h = fnv1a(normalize(s))` 为键，**同一 `en` 只能存活一种译法**，官方记忆里
1-en-多-zh 的重复条目在运行时结构上不可达 —— 删掉键行不会让任何「可命中的译法」消失。
`--no-coverage-en-equiv` 可关掉第 ③ 类（关掉后这 6 条导致整体放弃，便于复核这条判断；实测输出
「覆盖证明失败：6 条，已整体放弃（一个文件都没写）」）。

**本轮第 ③ 类为 0 不是退步**：上一轮（守卫上线前）有 6 条要靠 en 等价兜底；这一轮歧义守卫把它们挡在插入侧、
作为保留行留在包里（§3.4.4），于是不再需要 en 等价兜底 —— 守卫生效后，硬门禁的前两类就够用了。

**实测**（[reports/keyref-resolve-20261023-083154.json](../reports/keyref-resolve-20261023-083154.json)）：
`rows_before 10960` / `dropped 970` / `rows_after 9990` / `bytes_before 3695878` / `bytes_after 3504392` /
`coverage_verified true`（941 + 29 + 0）/ `by_mod {Squad 959, ReStock 6, KSPCommunityFixes 2, RealismOverhaul 2, ProceduralFairings 1}` / `ok true`。
幂等：第二遍 `dropped 0`、**41 个文件 SHA256 前后一致**；`--dry-run` 不写盘。
只删键行、不碰非键行：被删的 970 行全部 `s` 以 `#` 开头（`drop_samples` 可核），其余行按原字节写回（`kept` 原样）。

**删完的两道自检**（都要过）：

- Lead 侧 `_scratch/audit_packs.py`（本轮实跑）：`{"files":41,"rows":9990,"keep_rows":88,"bad_h":0,"empty_t":0,"bad_placeholder":0,"bad_richtext":0,"bad_samples":[]}`
- 本侧加严探针（本轮实跑）：`{"files":41,"rows":9990,"bytes_total":3504392,"unique_h":9990,"dup_h":0,"keyref_rows":22,"bad_fields":0,"problems":0}`
  （字段集合恒 `{h,n,s,t,mod}`、全局无重复 `h`、`n == normalize(s)`、`h == fnv1a(n)`、`t` 非空、无控制字符、占位符多重集）
- **判据：`problems == 0` 且 `coverage_verified == true` 且 `drop_errors == []` 且 `keyref_rows == retained`。**
  注意最后一项：**不是 `s# == 0`**（见 §3.4.4）。

#### 3.4.4 「s# 归零」不是判据：22 条必须保留的键行

插入侧被歧义守卫 / 长度比门禁拒掉的键（代码里叫 `retain_keys`），删行时**故意保留**：既不删、也不报错，
计入报告里的 `retained`。理由很直接 —— **它们的官方中文在包里没有任何行代表，删掉就是真丢内容**。

本轮 22 条（全在 `Squad.jsonl` 前 23 行内）：

| 类别 | 条数 | 键 |
|---|---|---|
| 歧义（§3.5） | 14 | Big-S 机翼 `500206/500209/500212/500218`、`Description Creation Pending` `501782/501785/501788/501791/501794/501800/501803`、`Ore` 501007、`EVA Report` 501010、`Moving Parts Experts Group` 501675 |
| 长度比门禁 | 8 | 记录重力 500100（比值 0.148）、电能 500040/500083（0.133）、公关 501656、研发部门 501679、电量 501004、样本 501019、小型高级抓取单元 6002506 |

这 22 行当前**匹配不到**（`s` 是键），保留的价值是「不丢内容 + 将来按 `ctx` 分层时可用」，不是「当后备」。

**与上一轮数字的关系**（别把差异当回归）：上一轮（守卫上线前，`082140`）是 **9,979 行 / 3,503,004 B / s# 0**；
本轮是 **9,990 行 / 3,504,392 B / s# 22**。净 +11 行 = 插入侧少插 11 条（928 → 917）+ 删行时多留 22 条（992 → 970 + 22）
两项相抵；其中上一轮错插的那 1 条 TS-06 行已被 ① 重写清掉（§3.5）。

**① 会把键行写回来**：实测 2026-10-23 08:29 那次 `translate` 重写后，`s#` 立刻从 0 回到 992（行数 10,043），
要等 ②③④ 跑完才回到 22。所以「`s#` 收敛到 retained」不是一次性里程碑，而是**每次 ① 之后都要重新满足的不变式**。

### 3.5 歧义英文串不能盲选官方译文（插入侧守卫，v0.5 新增）

**事故**：`packs/zh-cn/Squad.jsonl` 曾出现这样一行 ——

```json
{"h": "fdca7360c2d7a5c1", "n": "Description Creation Pending", "s": "Description Creation Pending", "t": "TS-06是用于将火箭一分两半的装置，但外型更紧凑。…", "mod": "Squad", "ctx": null}
```

**成因**：官方译文记忆里这一句英文对应 **7 个不同官方中文** —— `#autoLOC_501782`（TD-06 分级分离器）、

## 4. P1 归一化 + P2 过滤（已完成）

### 4.1 归一化规则

按顺序执行，**顺序不能变**：

1. `Unicode NFKC` 归一（全角转半角、连字展开）。

3. 连续空白（含制表符、不换行空格 `\u00A0`）折叠为单个空格。

- **开关**：将来若要重开必须走 `harvest.py` 的过滤器开关并**先在 3,193 条上试跑**，确认「只剩下 0 条可救」才准关——按今天的实测，会有 993 条白扔。

## 5. P3 遮蔽（本文最关键的一节）

### 5.1 为什么必须遮蔽

§1.5 的两个失败案例说明：模型看到"像代码"的东西会犹豫。但还有更隐蔽的：**即使译对了，也可能被模型"顺手美化"**——改空格、把 `/` 改成 `／`、把 `#FF8000` 的大写改小写。这些在 UI 里都会直接坏掉。

所以策略是：**凡是不该动的片段，送进去之前就换成哨兵，让模型根本看不见原文。**

### 5.2 两类处理

**A 类：不遮蔽，只校验。**

| 元素 | 例子 | 为什么不管 |
|---|---|---|
| KSP 占位符 | `<<1>>` `<<2>>` | 实测保留率 100%，且模型需要看到它来判断语序（"<<1>> 已掉落" vs "已掉落 <<1>>"） |
| TMP 富文本标签 | `<b>` `<color=#FF8000>` | 同上，标签位置影响语气 |
| printf / 格式符 | `%s` `{0}` | 同上 |

这三类**必须让模型看见**，因为中文语序和英文不同，遮蔽掉反而译不好。靠 §7 的校验门禁兜底。

**B 类：遮蔽。**

| 元素 | 例子 | 遮蔽为 |
|---|---|---|
| 文件路径 | `GameData/RealFuels/Resources.cfg` | `<<M0>>` |
| URL | `https://github.com/...` | `<<M1>>` |
| 配置键 / 类名 | `ModuleEnginesFX` `RealFuels` | `<<M2>>` |
| 转义序列 | 字面 `\n` `\t` `\\` | `<<M3>>` |
| 代码片段 | 反引号包围的内容、`{}` 里的表达式（非占位符时） | `<<M4>>` |
| 玩家/存档变量 | `<Kerman name>` 之类模板 | `<<M5>>` |

### 5.3 为什么哨兵长这样

用 `<<M0>>` `<<M1>>` 而不是 `⟦0⟧` `{{0}}` 的理由：

1. **和 KSP 自己的占位符同一形状**（`<<n>>`），实测这个形状保留率 100%。
2. 加 `M` 前缀保证不与真实占位符 `<<1>>` 冲突。
3. 纯 ASCII，不会被 NFKC 改动。
4. 校验时用一条正则 `<<M\d+>>` 就能清点，简单。

还原表跟着批次走：`{ "1": { "M0": "GameData/RealFuels/Resources.cfg" } }`。

### 5.4 遮蔽后的效果

    原文: Config: GameData/RealFuels/Resources.cfg
    遮蔽: Config: <<M0>>
    译文: 配置文件：<<M0>>
    还原: 配置文件：GameData/RealFuels/Resources.cfg

    原文: Line one\nLine two
    遮蔽: Line one<<M0>>Line two
    译文: 第一行<<M0>>第二行
    还原: 第一行\n第二行

第二个例子要特别注意：遮蔽 `\n` 后两个句子会粘在一起，所以遮蔽时**保留一个空格**：`Line one <<M0>> Line two`，还原时把空格连同哨兵一起换回。

### 5.5 遮蔽的边界条件

- 遮蔽后如果整条文本只剩哨兵（比如 `"GameData/x.cfg"` 整条），直接标 `keep`，不送翻。
- 一条文本里的遮蔽顺序按**从左到右、长匹配优先**，否则 `GameData/x.cfg` 可能被 `ModuleEnginesFX` 的规则先咬掉一部分。
- 还原必须做**完整性检查**：还原后哨兵残留数必须为 0，否则整条作废重试。

## 6. P4 打包

### 6.1 每条文本要带什么上下文

只给模型一句英文，它无法判断 `Run` 是"运行"还是"跑"。所以每条要带最小上下文：

| 字段 | 来源 | 例 |
|---|---|---|
| `t` | 原文 | `Run` |
| `role` | 由 `key` / `field` 推导 | `button` / `part_title` / `part_description` / `label` / `window_title` |
| `mod` | 目录名 | `RealismOverhaul` |

**不带**的（避免污染）：

- 完整 Localization key（`#VSR_theme_name` 这种会诱导模型按字母猜）。
- 文件路径。
- 玩家的 mod 加载顺序。

### 6.2 分批策略

| 批次类型 | 批大小 | 条件 | 理由 |
|---|---|---|---|
| 短文本批 | 200 | `len ≤ 30` 且无富文本无占位符 | 实测 200 条 17.4 s，性价比最高 |
| 中文本批 | 120 | `31 ≤ len ≤ 200` | 控总 token |
| 长文本批 | 20 | `len > 200` | 一条就几百 token |
| 富文本批 | 60 | `rt = true` | 单独批好在失败时整批重试 |
| 占位符批 | 40 | `ph = true` | 同上，占位符错误代价最高 |

按 `mod` **不做连续切分**——同一个 mod 的文本分散在不同批次里没关系，因为术语一致性靠 §7 的术语表锁，不靠批次内相邻。

### 6.3 请求体

    {
      "model": "gemini-3.8-flash-high",
      "temperature": 0.2,
      "reasoning_effort": "none",
      "messages": [
        { "role": "system", "content": "<见 §8 的 system prompt>" },
        { "role": "user",   "content": "<json: {glossary, batch:[{id,t,role,mod}]}>" }
      ]
    }

### 6.4 并发与重试

- 并发 **4**（实测安全），失败退避重试 3 次（1s / 4s / 16s）。
- 重试仍失败 → 该批拆半重试；单条仍失败 → 标 `failed`，不阻塞其他条。
- 每批记录 `finish_reason`，非 `stop` 一律视为可疑并重试。
- 老规矩：**整批 JSON 解析失败不要重译全部**，先尝试修复（剥围栏、补右括号），修复不了再重译。

## 7. P6 校验门禁

出来之后的八条硬门禁。**任何一条不过，该条作废，不写库。**

| # | 门禁 | 判据 | 不过的后果 |
|---|---|---|---|
| G1 | 条数一致 | 返回条数 == 请求条数；id 集合相等 | 错位，整批作废 |
| G2 | 占位符多重集一致 | `<<n>>` 的计数与编号完全一致（顺序可变） | **直接崩 UI**（KSP 会抛 Format 异常） |
| G3 | 格式符一致 | `{n}` `%s` 计数一致 | 崩 UI |
| G4 | 富文本标签一致 | 标签名与成对性一致；`<color=` 的色值逐字节一致 | 渲染错乱 |
| G5 | 哨兵全部还原 | 还原后 `<<M\d+>>` 残留 = 0 | 界面上出现 `<<M0>>` |
| G6 | 长度比 0.15–1.8 | `len(zh) / len(en)` 在此区间 | 太短=过度压缩丢信息，太长=按钮溢出 |
| G7 | 术语一致 | 与 `glossary` 已锁定的译法逐字一致 | 质量事故 |
| G8 | 非空且非原文 | 译文 ≠ "" 且 ≠ 原文（除非标了 `keep`） | 白花钱 |

**G2 是唯一会直接导致游戏报错的门禁**，优先级最高。

### 7.1 长度比的实测意义

中文通常比英文短 30–40%，所以 `0.4–0.9` 是常态区间。设 `0.15` 下限是为了抓"只翻了一个词"；`1.8` 上限是为了抓"模型加了解释"。

## 8. 人设与 prompt

### 8.1 用户要求

"提醒 llm，你是一个专业的航天工程师。" —— 这一条不是客套，它对质量有实质影响：KSP 的文本里 `Apoapsis` / `Specific Impulse` / `Ullage` / `Gimbal` 这些词，通用译者会译错，航天背景的译者不会。

### 8.2 system prompt（正式版，可直接用）

    你是一位资深航天工程师（航天推进与飞行力学方向），同时是 Kerbal Space Program 的资深玩家。
    你正在为 KSP 的中文汉化项目做英译中。

    【输出格式】
    只输出 JSON：{"items":[{"id":<id>,"zh":"<译文>"}]}
    不输出解释、不输出 markdown 代码围栏、不在 JSON 前后加任何字符。
    id 必须与输入一一对应，不增不减。

    【绝对不可改动】
    - KSP 占位符 <<1>> <<2>>：数量和编号必须完全一致，位置可随中文语序调整。
    - 格式符 {0} {1} %s %d：数量和顺序不可变。
    - 富文本标签 <b></b> <i></i> <color=...></color> <size=...>：标签与属性值逐字节保留。
    - 哨兵 <<M0>> <<M1>>：原样保留，不得翻译、不得删除、不得改编号。
    - 缩写保持英文：EVA、IVA、KSC、VAB、SPH、RCS、SAS、TWR、Δv。
    - 单位保持原样：m/s、kN、kg、atm、km、Mm。

    【术语（必须逐字使用，优先级高于你的个人习惯）】
    <这里注入 glossary，一行一条：English=中文>

    【风格】
    - 面向玩家，简洁、专业、不口语化，不加感叹号。
    - 按钮与标签尽量不超过 6 个汉字。
    - 部件名称保留型号数字与字母（如 OX-4M、RV-105），只译描述性部分。
    - 已经是专有名词的 mod 名、公司名、人名不译。

    【专有约定】
    - Booster=助推器，Oxidizer=氧化剂，Throttle=节流阀，Gimbal=万向节，
      Specific Impulse=比冲，Apoapsis=远地点，Periapsis=近地点，
      Delta-V=Δv，Center of Mass=质心，Center of Pressure=压心，
      Reaction Wheel=动量轮，Monopropellant=单组元推进剂。

### 8.3 术语表怎么来（v0.3 更正：它是「官方译文记忆」2,126 条，不是三层术语表）

先纠正一个叫法：`packs/glossary.jsonl` 今天**不是术语表**，是 **Squad 官方译文记忆 2,126 条**。它一份数据三档用法（`translate.py` 报告里的 `glossary_detail` 原文：`{"total":2126,"terms":813,"locked":588,"exact":1868,"keyref":2126,"bad":0}`）：

| 用途 | 条数 | 字段 | 说明 |
|---|---|---|---|
| 整句直用 | **1,868** | `exact` | 池里的英文与官方英文逐字相同 → 直接用官方中文，零 token |
| 术语注入 | **813** | `terms` | 批内出现就注入 prompt，钉死官方译法（§8.4） |
| 键引用直用 | **2,126** | `keyref` | 池里那条是 `#autoLOC_xxx` 键引用 → 按 key 取官方中文（`--keyref-rescue`，默认关） |
| 短语级锁（G7） | **656**（锁表 **588**） | 摘要串 / `locked` | 两个数口径不同：656 按「短语级命中」计，588 按「最终锁定的术语表」计，引用时要说清是哪个 |

原始产出（`python -m i18n_tools.glossary`，2026-10-23 本机实测）：Squad cfg 文件 **533**（其中有英文注释的 443 个）；行尾注释命中 **3,290 处 → 2,126 个唯一键**（同键不同英文 12 处，取首次出现）；字典 zh-cn 键 **12,028**；配对 **2,126 / 2,126**（只有中文 9,902 / 只有英文 0）；`short`（英文 ≤5 词且 ≥4 字符）**887 条**；输出 2,126 行 / 467,238 字节，耗时 0.12 s。

另两路来源（存量中文补丁 2,408 条赋值 / 唯一值 2,224；LLM 抽高频专名）仍按 v0.2 记录，**本轮没有重跑**，等 B13 落地时一起做。

#### 8.3.1 官方双语对怎么抽（不是直接读字典）

`Squad/Localization/dictionary.cfg` **只有 zh-cn 一个语言节点**（12,031 行赋值 / 12,028 个唯一键，891,576 字节，BOM+CRLF，没有任何 en-us 节点），里面没有英文 —— 直接读它拿不到任何「英文→中文」对。这一点是下面所有口径问题的根。

英文原文在 Squad 自己的 cfg 的**行尾注释**里：

```
title = #autoLOC_500460 //#autoLOC_500460 = S1 SRB-KD25k "Kickback" Solid Fuel Booster
```

所以抽取是三步（`glossary.py` 文件头 1–38 行把这三步的坑都写明了）：

1. 扫 `GameData/Squad/**/*.cfg`（533 个文件），用正则 `COMMENT_EN_RE = re.compile(r"#(autoLOC_\d+)\s*=\s*([^\r\n]+)")` 抓行尾注释里的英文 —— **但必须跳过 `Localization/` 目录**（这 533 个文件里唯一的 `dictionary.cfg` 就在那儿）→ 本机实测 **3,290 处 / 2,126 个唯一键**；
2. 用 key 去 `dictionary.cfg` 的 zh-cn 节点取中文 → 配对 **2,126 对（100%）**。**配对时必须补 `#`**：注释里是 `autoLOC_500460`，字典里是 `#autoLOC_500460`，少这个 `#` 配对数为 0；
3. 反方向：字典里有 **9,902** 个键没有任何英文注释（其中 98 个是 `#autoLoc_` 小写 l 驼峰变体），默认不写入；加 `--include-zh-only` 才导出（`en` 为空串）。

#### 8.3.2 旧数字 11,930 / 11,841 / 8,318 为什么作废（口径错误，不是笔误）

上一轮记的三条数字错在同一件事上：**把 `dictionary.cfg` 自己也算进了「英文来源」**。

- `dictionary.cfg` 里有 12,031 行 `#autoLOC_N = 中文`，它们**全部**匹配 `#(autoLOC_\d+)\s*=\s*([^\r\n]+)` → 于是「英文表」里 99% 是中文，唯一键数变成 **11,930**；
- 换句话说：**11,930 是字典里 `#autoLOC_` 形式的键数，不是英文条数**；
- 「11,841 对」和「≤5 词短术语 8,318 条」都建立在这张错表上，不可复现 → **一并作废，不要在新文档里引用**。

真实英文只存在于 Squad cfg 的 **3,290 处行尾注释**里，去重后 **2,126 条**。这个坑在 `tools/i18n_tools/glossary.py` 文件头 1–38 行与 `tools/README.md` 的口径对照表里都留了记录。

#### 8.3.3 它对池子的实际覆盖（按 2,126 条重算，别高估）

| 指标 | 实测（2026-10-23，我自己数 `packs/pool.jsonl` 的 12,792 行） |
|---|---|
| 池子唯一文本 | 12,792 |
| 与官方英文**逐字相同**（可零 token 直用） | **35 条**（旧值 45 建立在错表上，一并作废） |
| 池里是 `#` 键引用、官方记忆能按 key 给出中文 | **993 条**（`#autoLOC_` 前缀 1,232 条；其余 1,961 条是 mod 自有键，记忆命中 **0**） |
| 术语注入的覆盖 | **未重算**：抽取规则变了，等 B13 按新表重算后再填 |

结论不变：**官方译文记忆是「提一致性 + 救键引用」的工具，不是「省翻译量」的工具**。指望它减少 LLM 调用是错的，但它能把批内出现的官方译法（"远地点"而非"远拱点"）钉死，这正是 §1.5 术语漂移问题的正解。

**官方字典优先**：玩家已经在游戏里见过 Squad 的译法（"远地点"而不是"远拱点"），我们的译法必须跟它对齐，否则同一个界面里两种叫法。

### 8.4 glossary 注入方式

只注入**本批出现过的**术语，不注入全表。全表几千条会挤爆 prompt，而且稀释注意力。

批内术语量控制在 30–60 条。

## 9. P7 复核（解决术语漂移）

### 9.1 三道工序

1. **批内自检**：一批译完后，把 `glossary` 里出现的术语对照一遍，不一致的标 `term-drift`。
2. **跨批复核**：全部跑完后，按 `源文本哈希` 分组——同一个源文本只能有一个译法。出现多个（说明同一条被重复翻译过，通常是重试或分片重叠）→ 取票数最高的，其余丢弃。
3. **术语专项复核**：把所有 `term-drift` 条目按术语聚合成小批（每批 50 条），单独送一次"只改这一处"的复核请求。

### 9.2 术语锁定闭环

    术语表 v1（官方字典 + 存量补丁）
        ↓
    批量翻译（带 glossary）
        ↓
    术语漂移检出 → 人工/规则裁决 → 术语表 v2
        ↓
    只重译受影响的条目（按术语反查）

**关键**：术语表更新后，不是全量重译，而是**按术语反查受影响条目**重译。否则每改一个词就要重花一次全量成本。

## 11. 数据流接口

`pool.jsonl`（P0–P2 产物），每行：

    {"id":1,"h":"9f2c...","text":"Switch to Hangar","src":"loc","mod":"RealismOverhaul","field":null,"key":"#RO_switch","ph":false,"rt":false,"dg":false,"path":false,"url":false,"len":16}

### 11.2 输出

`packs/<lang>/<modId>.jsonl`（**JSONL，唯一运行时格式，D35**；`<lang>` 目前只有 `zh-cn`），每行就是 `DictPack.LoadJsonLines` 吃的格式：

    {"h":"9f2c...","n":"Switch to Hangar","s":"Switch to Hangar","t":"切换至机库","mod":"RealismOverhaul","ctx":null}

| 字段 | 含义 | 约束（来自 Core 的解析器，不是约定） |
|---|---|---|
| `h` | `Fnv1a64(utf8(归一化原文))`，**16 位小写 hex 字符串** | 与 Core 的 `Fnv1a.Hash` 必须逐位一致；`Dict/JsonLineReader.cs:90` 要求该字段存在，缺失整行 ParseError |
| `n` | 归一化原文（§4.1 五步） | 查表用 |
| `s` | 原文（未归一化） | 命中时逐字比对，兜 FNV 碰撞；不等按 miss |
| `t` | 译文 | `JsonLineReader.cs:102` 要求**非空**，否则整行 ParseError |
| `mod` | 归属 mod | 冲突仲裁用（00 §4.1） |
| `ctx` | 可选上下文 | 三层键里的 ctx 层（00 §4.1），可缺省 |

**旧字段表作废**：v0.2 这里写的是 `dict/zh-cn/<mod>.json` 加 `{h,src,zh,status,ts,model,promptV,glossaryV}` —— 那是设计期猜想，与实现不一致（目录、扩展名、字段名全不同）。`model / promptV / glossaryV / status` 这些**不进字典**，它们只在两处：缓存键（§11.3）与 `reports/` 的逐条报告。字典只带运行时查表要用的东西 —— 多一个字段就是多一次解析。

**h 字段的一个真实坑（T8）**：如果 `h` 恰好是「16 位全数字」的 hex 串（例如 `8400081244540915`），解析器**必须按 hex 解析**，不能被十进制 `TryParse` 抢走（真值是 `0x8400081244540915 = 9516546049249841429`）。`packs/pool.jsonl` 里踩中这个歧义的有 **12 行**，回归测试是 `tests/UI18n.Core.Tests/CorpusContractTests.cs:342–362` 的 `AllDigitHexRowsInSample_ParseToTheirTrueHash`。

### 11.3 缓存键

    key = FNV1a(text) + "|" + glossaryV + "|" + promptV + "|" + model

四者任一变化就必须重译。这样改一次 prompt 只重跑"确实受影响"的，而不是全量。

## 12. 失败模式与对策

### 12.1 流水线级失败（设计期已知）

| 失败模式 | 症状 | 对策 |
|---|---|---|
| 整批 JSON 坏 | 解析抛异常 | 先修（剥围栏、补括号），修不了再拆半重译 |
| 丢条 / 多条 | G1 门禁不过 | 整批作废，拆半重译 |
| 占位符被改 | G2 门禁不过 | 单条重译；连续 2 次失败标 `failed` 保留原文 |
| 术语漂移 | G7 门禁不过 | 记入 `term-drift`，走 §9 的复核 |
| 模型加了说明 | 输出不是 JSON | 剥壳重试；仍不行降批 |
| 超时 | 请求超时 | 退避重试；连续超时降并发 |
| 模型把中文又译回英文 | 译文全是 ASCII | G8 + 语言检测拦下 |
| 上下文串味 | A 条译文出现在 B 条 | G1 的 id 对齐拦下 |

### 12.2 模型行为与对策（实测 4 个坑）

这一节是本轮真跑出来的东西，不是推演：`reports/` 里 16 个报告只有 **3 个是 `offline=false`** 的真跑（**014753** limit 200：req 198 / ok 196 / failed 2 / drift 5 / mixed 9；**015132** limit 200：ok 197 / keep 1 / drift 6 / mixed 9；**015152** 真写盘：ok 24 / written 25 条 = 6 个 mod 的包）。其余 13 个是 `offline=true dry_run=true` 的桩跑（输出被加了 `【离线】` 前缀），**不能当证据**。

| # | 坑 | 实测证据 | 对策 |
|---|---|---|---|
| 1 | **半译**：一句里一半中文一半原样英文 | **旧口径 `mixed_lang 594` 作废**（那是未分类的原始残留：`<color=white>` 里的 color/white、字面 `\n` 后的 nDSN、`@/missionPayload.Print()` 表达式、rpm/hp/km/dBi 单位）。按交付报告的两桶口径全量重算：残留 ≥3 词的 **241 条 = `brand_residue` 102 + `true_mixed` 139（1.41%）**；`brand_residue` 是源文本来就以大写/含数字形式出现的专名（Falcon 9、Bluedog Design Bureau、Delta IV），**不算缺陷**。逐条样本 `reports/sample-20261023-015132.jsonl`（200 行：ok 197 / keep 1 / failed 0 / gates 全空 / drift 6 = 3.0%） | G6 混合语言门禁 + 单条重试（§7）；两次不过转人工；统计时先剔 `brand_residue` 再算率（口径见 `reports/DELIVERY.md` §8） |

| 4 | **哨兵会静默丢内容** | 离线桩报告 `translation-20261023-014537.json` 里大量 `"why":"哨兵多重集 期望{'<<M0>>': 1} 实际{}"`：模型把遮蔽占位符整段吞掉，句子读着通顺但少了一截 | G5 哨兵多重集门禁（八条门禁里优先级最高）+ 全池 12,792 行实测**已无 `<<M\d+>>` 残留**；`translate --selftest` **12,815 项检查 0 失败** |
