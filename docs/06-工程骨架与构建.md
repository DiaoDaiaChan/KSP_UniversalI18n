### 3.4 为什么测试跑 net10.0，而插件跑 net472

| 目标 | 用在哪 | 为什么 |
|---|---|---|
| `net472` | `src/UI18n.Core`（KSP 侧）、`src/UI18n.Runtime` | KSP 1.12.5 的运行时是 .NET Framework 4.7.2 / Mono 5.x；只有编到 net472 才能引用 `Assembly-CSharp.dll` 这类老程序集 |
| `net10.0` | `tests/UI18n.Core.Tests`、命令行工具 | 本机只装了 `Microsoft.NETCore.App.Ref 10.0.12`，**net8.0 反而编不了**（没有一个 8.x 的 ref pack）。测试要的是「能在 `dotnet test` 里跑」，不是「跟游戏同运行时」 |

补充两点，避免后来者重新踩：

- **没有 mono 可以跑 net472 测试。** 本机 `MonoBleedingEdge` 的 `bin` 缺失（没有 `mcs` / `mono` 可执行），
  所以在 Windows 上「用 net472 跑 xunit」要依赖完整 .NET Framework 工具链，不值得为单测引入。
- **Core 是纯 .NET，两个目标编的是同一份源码。** 测试在 net10.0 上验证逻辑；net472 那次构建额外验证
  「老 BCL 里有这些 API + 语言级别 9.0 能编过」。所以 `dotnet build UI18n.sln` 必须**两个目标都编过**才算绿。

### 3.5 `Directory.Build.props` 里那 6 条设定的理由

| 设定 | 值 | 理由 |
|---|---|---|
| `LangVersion` | `9.0` | 与 net472 的 BCL 能力对齐；用 C# 10+ 语法（文件级 namespace、`required`）在 net472 上会引出一堆兼容问题。个别项目要更新语法，在自己的 csproj 里覆盖（后定义者胜） |
| `Nullable` | `disable` | net472 无法真正做可空引用校验，开着只产生噪音 |
| `GenerateDocumentationFile` | `false` | 不产 xml 文档，避免每个 public 成员一条 CS1591 |
| `Deterministic` | `true` | 同一输入必须产出同一字节流 —— 差分发布与 CI 校验的前提 |
| `EnableNETAnalyzers` | `false` | 关掉 CA* 噪音，让警告列表只剩「引用冲突」这类真问题 |
| `TreatWarningsAsErrors` | `false` | 不把警告当错误（Unity 老程序集会产生无法修的历史警告） |

### 3.6 引用游戏程序集时的三条规矩

1. **`Private = false`（Copy Local 关掉）。** 这些 DLL 游戏里已经有了，拷进 `build/` 既浪费又会造成「同一程序集两版本」的加载冲突。
2. **路径集中定义，不要在每个 `HintPath` 里各写一遍。** 用 `$(KspDir)` 这类属性在 Runtime 的 csproj 里定义一次。
3. **`Input` / `KeyCode` 必须额外引 `UnityEngine.InputLegacyModule.dll`。** 只引 `UnityEngine.dll` 会得到
   `error CS0103: 当前上下文中不存在名称"Input"`（03 §6.4 的实测坑）。

本机实测的引用面（`D:\Kerbal Space Program_newmod\KSP_x64_Data\Managed\`）：

|---|---|---|
| `Assembly-CSharp.dll` | 10,790,912 B | `KSP.Localization.Localizer`、`KSPAddon`，GUILayout 调用面所在游戏代码 |
| `UnityEngine.CoreModule.dll` | 1,005,568 B | `GUIContent` / `GUIStyle` / `Rect` |
| `UnityEngine.UI.dll` | 225,792 B | `UnityEngine.UI.Text.set_text`（uGUI 通道） |

|---|---|
| 只跑某个测试类 | `pwsh tools\run-tests.ps1 -RunnerArgs '-class','UI18n.Core.Tests.DictPackTests'` |

### 6.5 Packs 布局：两条致命缺陷与部署判据

> 这一节写成**判据**，不写成建议：任何一条不满足，运行时的表现都是「插件正常加载、patch 全部装上、一个词都不译」，
> 而且日志里**不一定有 error**。

#### 6.5.1 判据 1：字典只从 `Packs/<lang>/*.jsonl` 读 —— 平铺在 `Packs\` 根下的文件等于没装

- 代码事实：`src/UI18n.Runtime/ConfigLoader.cs` 的 `LoadPacks` 用
  `Directory.GetFiles(dir, "*.jsonl", SearchOption.TopDirectoryOnly)` 扫 `Packs/<lang>/`（第 156 行），`dir` 由语言候选拼出
  （`zh-cn` → 先试 `Packs/zh-cn`，再试 `Packs/zh`）。
- 踩过的坑：早期实现平铺读 `Packs\` 根下的 `*.jsonl`，而部署按契约把包放在 `Packs\<lang>\` → **一条都读不到，字典恒空**。
  症状不是崩溃，是「patch 装上了、界面全英文」。
- 自证（三条日志，缺一条就是没读到）：
  - 正面：`pack loaded: zh-cn/RP-1.jsonl, entries=+3`（每个文件一行）
  - 正面：`dictionary: entries=N, parseErrors=0`（N > 0，且 parseErrors 必须是 0）
  - 反例：`no pack dir for language=zh-cn (looked for … under …), dictionary is empty` / `no *.jsonl in …` / `packs dir not found: …`
- **判据**：装完之后 `Get-ChildItem GameData\UI18n\Packs\<lang> -Filter *.jsonl` 至少一个文件，且日志里 `pack loaded:` 的行数与它**一样多**。

#### 6.5.2 判据 2：源产物（`pool.jsonl` / `glossary.jsonl` / `inventory.json`）绝不许进 `Packs\`

- 代码事实：解析器要求 `h`（`src/UI18n.Core/Dict/JsonLineReader.cs:90`）与非空 `t`（`:102`）；源产物没有 `t`（它们有 `text`），
  于是**每一行都是 ParseError**。
- 实测（把已编译的 Core 拉进来灌真实文件，不等游戏启动）：

| 文件 | 行数 | entries | parseErrors |
|---|---|---|---|
| `packs/pool.jsonl` | 12,792 | **0** | **12,792** |
| `packs/glossary.jsonl` | 2,126 | **0** | **2,126** |
| `src/UI18n.Runtime/smoke/_smoke.jsonl` | 34 | **34** | **0** |

- 踩过的坑：旧版部署会把 `packs\{pool,glossary}.jsonl` 当字典拷进 `GameData\UI18n\Packs\` → 每行 ParseError、字典恒空；
  因为「文件明明在」，排障时最容易被误判成编码问题。
- **判据**：`parseErrors == 0`。出现 `parseErrors == 文件行数` 时，**先怀疑装错了文件，不要查编码**。

### 6.6 PackLocator：Packs 布局判据的代码化（事故回归锁）

**事故一句话**：Runtime 里手写的包发现逻辑用 `Directory.GetFiles(Packs, "*.jsonl", TopDirectoryOnly)` 平铺读根目录，
与 D35 契约 `Packs/<lang>/<modId>.jsonl` 不符 —— 于是**按契约放的包一条都读不到、字典恒空、patch 恒 0**。
这一层（net472 + 依赖游戏侧程序集）在本机没法单测，所以它是**装进真游戏才发现的**；
现在把纯路径计算搬进 Core，让「优先级 / 回退 / 平铺文件永不读」三件事能被单测穷举，不会再退回「装进游戏才发现」。

| 文件 | 大小 | 作用 |
|---|---|---|
| `src/UI18n.Core/Dict/PackLocator.cs` | 25,817 B | 实现：语言归一化 / 候选回退 / 目录选择 / 文件枚举 / 诊断 |
| `src/UI18n.Core/Dict/README-PackLocator.md` | 7,809 B | API 契约、优先级规则、与提案的差异、Runtime 接线示例 |
| `tests/UI18n.Core.Tests/PackLocatorTests.cs` | 23,563 B / **81 例** | 穷举每一条规则，含 2 条事故回归锁 |
| `tests/UI18n.Core.Tests/PROPOSAL-PackLocator.md` | 21,075 B | 提案与事故复盘（写代码前的原始设计） |

API（`namespace UI18n.Core.Dict`）：`NormalizeLanguage` / `LanguageCandidates` / `SelectLanguageDir`（纯函数版 + I/O 版）/
`ListPackFiles` / `Resolve` → `PackResolution`（状态 + 命中目录 + 文件 + 诊断 + `Describe()`），
状态枚举 `PackDirStatus { Found, PacksRootMissing, LanguageDirMissing }`。

**写死的七条规则**（细节见 `README-PackLocator.md` §2）：

1. 归一化 Trim → `_` 换 `-` → ToLowerInvariant（Invariant，避开土耳其 i）。
2. 候选：完整标签在前、主语言在后（`zh-cn` → [zh-cn, zh]），多段只回退一次。
3. **单向回退**：`zh-cn` 能落到 `zh/`，`zh` **不会**升到 `zh-cn/`。
4. 目录匹配先 Ordinal 精确、再 OrdinalIgnoreCase，返回磁盘真实大小写（不依赖文件系统行为）。
5. 文件枚举 `*.jsonl`、不递归、跳过 0 字节、按文件名 **Ordinal** 升序（顺序必须确定 —— 后写覆盖先写）。
6. **平铺文件永不读**：根下的 `*.jsonl` 只进 `FlatFileCount` 诊断字段。
7. **不抛异常**：根不存在 / 无权限 / 非法字符 / 语言为 null 一律返回状态枚举（红线 6：失败只 log 不抛，但必须能计数）。

**两条事故回归锁**（它们红了就说明又退回「装进游戏才发现」）：
`Resolve_FlatPacksUnderRoot_AreReportedNotSilentlyLoaded` —— 只有平铺包时必须给 `LanguageDirMissing` + `Files` 空 + `FlatFileCount==2`；
`Resolve_FlatPacksDoNotHideRealLanguageDirectory` —— 平铺包与真语言目录并存时只读真目录。

> **状态（v0.8 更新）：已实现 + 已单测（81 例全绿）+ Runtime 已接线，但接线后的构建还没进过游戏。**
> `src/UI18n.Runtime/ConfigLoader.cs` 第 134 行现在是 `PackResolution packs = PackLocator.Resolve(root, language);`，
> 第 123–124 行的注释把「不许再自己拼 Packs 路径或判断 `Directory.Exists`」写成硬规矩（那正是 P1 事故的复发路径）；

#### 6.7.1 发布来源标记：DLL 内嵌 `1.0.0+<commit>`

两个 DLL 的 `InformationalVersion` 是 `1.0.0+<40 位 commit>`，实测两批：

| 来源 | Core | Runtime | 内嵌版本串 |
|---|---|---|---|
| 已发布 zip 内 / 部署目录（round 2/3 验过的那一对） | 26,624 B `3C33CB556614E935…` | 43,520 B `D906F956A4D0DF36…` | `1.0.0+fc1c2b20d7f53ef8e071d8de2ed97fdaa266b850` |
| `build\bin\Release\net472`（9238f1a 之后重建） | 26,624 B `BBD022FB727F6C55…` | 43,520 B `4357C25ED750B3DE…` | `1.0.0+9238f1acc43f8249be734ceb2e2dccf2d6920ad0`（= `git rev-parse HEAD`） |

三句话（这三句就是判据）：

1. **发布物必须从干净工作树构建。** 首个 1.0.0 zip 是脏树构建的：构建时 `HitSampleLimit` 等改动还没提交，内嵌的 `+fc1c2b2` 里**没有对应源码** ⇒ 二进制声称的 commit 不包含它的源码（事故记录见 §6.8 坑 6）。
2. **DLL 内嵌 `1.0.0+<commit>` 是有意的来源标记**，不是调试残留 —— 它让「这个 dll 是哪个 commit 编的」在二进制里可查（读法：按 UTF-16LE 搜 `1.0.0+`）。
3. 因此 **「同一 commit 重建 == 发布字节」成立，跨 commit 一定不同** —— 这不是不确定性，是 .NET SDK 把 `SourceRevisionId` 追加进 `InformationalVersion` 的既定行为。

> 出包前判据：`git status --porcelain` 为空 **且** 两个 DLL 内嵌的 sha 等于 `git rev-parse HEAD`。
> 守卫由 `build-release.ps1` 承担（加 `-AllowDirty` 开关、**默认拦脏树**；本轮由 core-engineer 落地，落地前脚本仍是 9,038 B 的旧版、没有这道检查）。

> **zip 的字节数与 sha256 每次出包都会变，不要拿它当回归断言。**
> 原因：zip 条目里存文件时间戳，`UI18n.version` 每次都被重写（`VERSION` 换成 `-Version`），所以同样的源码两次出包
> 得到的 zip 字节不同、sha256 也不同。对外只认**当次** `manifest.json` 里的 `zip.sha256`（netkan 的 `download` + `sha256` 就从这里生成）。
> **稳定、可作回归断言的是四个字段：`files` / `packFiles` / `packRows` / `packBytes`。**

### 6.8 验证轮（round）的取证与读日志：六个坑

验证轮最容易出的问题不是「插件坏了」，而是**证据本身是假的**。下面六条是 round 1 / round 2 真踩到的（坑 6 发生在出包侧，但错法同源：把「我编了」当成「产物来自这个 commit」），写在前面免得下一轮再交一次学费。

**坑 1 · 截图拍到了桌面，不是游戏。** round 1 的 `verify-20261023-090354.png`（764.4 KB, 3440x1440）拍下来是桌面 ——
截图那一刻 KSP 是 `iconic=True`（最小化，窗口矩形 `-32000,-32000`），`CopyFromScreen` 抓的是屏幕，不是游戏窗口。
正确姿势（Lead 手工复核用的就是这条）：`ShowWindow(SW_MAXIMIZE)` + `SetWindowPos(HWND_TOPMOST)` → 等 2 s → `CopyFromScreen`，
产物 `build/shots/verify-topmost-092820.png`。
**教训**：截图取证必须**先断言目标窗口在前景且未最小化**，断言不过就打 `shot: SUSPECT` 并让本轮判为「证据不足」——
否则「我们拍了张图」是一句没有信息量的话，而且看起来像证据。

**坑 2 · 探针 auto-stop 抛 `System.ArgumentException`，是探针自己的问题。** 日志第 295 行：

```text
[ERR 09:21:43.298] [UI18n] [probe] window contents failed: System.ArgumentException: Getting control 6's position in a group with only 6 controls when doing repaint
```

它只发生在探针 DLL 内（探针到点自己停止绘制，GUILayout 的组计数与上一趟 Layout 对不上），**运行时零影响**，探针随后已从磁盘移除（第 38 行 `probe removed from disk: True`）。
看到这一条不要当成产品故障去查 Runtime。

**坑 3 · 「错误行」统计有假阳性。** round 1 的汇总打印 `UI18n error lines: 3`（第 296 行），但其中 2 条是字典装载行（第 297–298 行），
只因为它们含有 `parseErrors` 这个词就被 `error` 关键字捞进来了；真正的 ERR 只有坑 2 那一条。
**教训**：读 `error lines` 之前先看那几行原文，别把计数当故障数。

**坑 4 · 启动时间是观测值，不是耗时基准。** round 1 的 `verdict=mainmenu after 481s (log 24,882,195 B)`（第 28 行）比历史慢，
但这一轮装了探针 DLL、且 42 个包 / 10,024 条字典是首次加载，**没有做对照** —— 写文档、下结论时只能写「本轮观测 481 s，归因待 round 2」。

**坑 5 · dwell 死锁：进了主菜单，脚本却空转到被人工 kill。** round 2 的
`[09:47:31] verdict=mainmenu after 416s (log 24,876,024 B) -> dwell 60s`（`reports/verify-20261023-094034.log` 最后一行）
之后**再没有任何输出**，直到 09:53 人工 kill。
根因：dwell 判断原来嵌在 `if ($tail -match 'to MAINMENU|MAINMENU to')` 里面，而 `$tail` 只是 `Get-Content -Tail 300`；
KSP 进主菜单后仍每 20 s 写一次 patch stats（其它 mod 也在刷日志），那行 `MAINMENU` 滚出 300 行窗口之后条件永不成立 → dwell 永不触发。
修法（已落在 `_scratch/p1/round.ps1` 09:59 版：事故注释 `:104–107`、新逻辑 `:121–134`）：**判定一次就把 `$mainmenuAt` 锁住**，
把 dwell 检查提到 `-match` 外面。
**判据**：日志里出现 `-> dwell 60s` 之后，60 s 内必须再出现后续行（截图 / 汇总 / `final dump`）；
只有那一行、之后全空白 = 死锁，别坐着等 deadline。

**坑 6 · 从脏工作树出包。** 现象：`dist/UI18n-1.0.0.zip` 里两个 DLL 内嵌 `1.0.0+fc1c2b20d7f53ef8e071d8de2ed97fdaa266b850`，但那份 DLL 是**工作树脏的时候**编出来的 —— 构建时 `HitSampleLimit` 等改动还没提交，`fc1c2b2` 里**没有对应源码** ⇒ 二进制声称的 commit 编不出这份字节。
根因：.NET SDK 把 `SourceRevisionId`（= 构建时的 `git rev-parse HEAD`）追加进 `InformationalVersion`；工作树脏并不影响它取 HEAD，于是「源码不完整的构建」被标成了一个看起来正常的 commit。
**判据**：出包前 `git status --porcelain` 必须为空，**且** 两个 DLL 内嵌的 sha 等于 `git rev-parse HEAD`（读法见 §6.7.1）。守卫在 `build-release.ps1`：加 `-AllowDirty` 开关、**默认拦脏树**（本轮由 core-engineer 落地）。
**教训**：「我编了」不等于「发布物来自这个 commit」—— 脏树构建出来的包，内嵌 commit 是假的。
