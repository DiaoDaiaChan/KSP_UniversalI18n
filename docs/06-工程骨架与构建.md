三条摆放原则（为什么不是别的结构）：

1. **一个可执行产物一个项目。** Core 与 Runtime 拆开，是因为 Core 必须零游戏依赖（能跑在 CI 的 net10.0 上、能写单测），
   Runtime 必须引用 UnityEngine / Assembly-CSharp / 0Harmony —— 两者的依赖集天然互斥。Core 的 csproj 里有
   `UI18nCore_RejectGameDependencies` 目标，引用游戏程序集或任何 PackageReference 都会在编译前直接报错。
2. **数据与代码分离。** `packs/` 里放的是**产出**（JSONL），不进 `src/`，也不手工提交二进制（`.gitignore` 里那条 `packs/*.uip` 留作保险：D35 已把 `.uip` 降级为 deferred）。
3. **临时物永不入库。** `_scratch/`（探针骨架、基准、3 MB 语料）与 `_audit/`（反编译存档、原始 DLL）已写进 `.gitignore`；
   仓库里只留可复现的输入与可复现的产出。

### 3.4 为什么测试跑 net10.0，而插件跑 net472

| 目标 | 用在哪 | 为什么 |
|---|---|---|
| `net472` | `src/UI18n.Core`（KSP 侧）、`src/UI18n.Runtime` | KSP 1.12.5 的运行时是 .NET Framework 4.7.2 / Mono 5.x；只有编到 net472 才能引用 `Assembly-CSharp.dll` 这类老程序集 |
| `net10.0` | `tests/UI18n.Core.Tests`、命令行工具 | 本机只装了 `Microsoft.NETCore.App.Ref 10.0.12`，**net8.0 反而编不了**（没有一个 8.x 的 ref pack）。测试要的是「能在 `dotnet test` 里跑」，不是「跟游戏同运行时」 |

补充两点，避免后来者重新踩：

- **没有 mono 可以跑 net472 测试。** 本机 `MonoBleedingEdge` 的 `bin` 缺失（没有 `mcs` / `mono` 可执行），
  所以在 Windows 上「用 net472 跑 xunit」要依赖完整 .NET Framework 工具链，不值得为单测引入。
- **Core 是纯 .NET，两个目标编的是同一份源码。** 测试在 net10.0 上验证逻辑；net472 那次构建额外验证
  「老 BCL 里有这些 API + 语言级别 9.0 能编过」。所以 `dotnet build UI18n.sln` 必须**两个目标都编过**才算绿。

### 3.5 `Directory.Build.props` 里那 6 条设定的理由

| 设定 | 值 | 理由 |
|---|---|---|
| `LangVersion` | `9.0` | 与 net472 的 BCL 能力对齐；用 C# 10+ 语法（文件级 namespace、`required`）在 net472 上会引出一堆兼容问题。个别项目要更新语法，在自己的 csproj 里覆盖（后定义者胜） |
| `Nullable` | `disable` | net472 无法真正做可空引用校验，开着只产生噪音 |
| `GenerateDocumentationFile` | `false` | 不产 xml 文档，避免每个 public 成员一条 CS1591 |
| `Deterministic` | `true` | 同一输入必须产出同一字节流 —— 差分发布与 CI 校验的前提 |
| `EnableNETAnalyzers` | `false` | 关掉 CA* 噪音，让警告列表只剩「引用冲突」这类真问题 |
| `TreatWarningsAsErrors` | `false` | 不把警告当错误（Unity 老程序集会产生无法修的历史警告） |

### 3.6 引用游戏程序集时的三条规矩

1. **`Private = false`（Copy Local 关掉）。** 这些 DLL 游戏里已经有了，拷进 `build/` 既浪费又会造成「同一程序集两版本」的加载冲突。
2. **路径集中定义，不要在每个 `HintPath` 里各写一遍。** 用 `$(KspDir)` 这类属性在 Runtime 的 csproj 里定义一次。
3. **`Input` / `KeyCode` 必须额外引 `UnityEngine.InputLegacyModule.dll`。** 只引 `UnityEngine.dll` 会得到
   `error CS0103: 当前上下文中不存在名称"Input"`（03 §6.4 的实测坑）。

### 4.1 命令

**不要用 `dotnet test`。** 本机 VSTest 的 testhost 一启动就崩，一条用例都执行不到（三条路线的实测见 §4.2）。

`dotnet build tests\UI18n.Core.Tests\UI18n.Core.Tests.csproj -c Release` →
`dotnet tests\UI18n.Core.Tests\bin\Release\net10.0\UI18n.Core.Tests.dll` → `exit $LASTEXITCODE`（不吞任何退出码）。


| 目的 | 命令 |
|---|---|
| 只跑某个测试类 | `pwsh tools\run-tests.ps1 -RunnerArgs '-class','UI18n.Core.Tests.DictPackTests'` |
| 不重复构建 | `pwsh tools\run-tests.ps1 -NoBuild` |
| Debug 配置 | `pwsh tools\run-tests.ps1 -Configuration Debug` |
| 看 runner 支持的全部参数 | `dotnet tests\UI18n.Core.Tests\bin\Release\net10.0\UI18n.Core.Tests.dll -?` |

过滤器由 xunit.v3 自己解析（`-class` / `-class-` / `-method` / `-namespace` / `-trait` / `-filter "query"`）。
注意 `pwsh -File` 不做 PowerShell 的参数解析，`'-class','X'` 会当成一个含引号和逗号的字面量传进去 —— 脚本内部会按逗号拆分并剥掉成对引号，两种写法都能用。

### 6.5 Packs 布局：两条致命缺陷与部署判据

> 这一节写成**判据**，不写成建议：任何一条不满足，运行时的表现都是「插件正常加载、patch 全部装上、一个词都不译」，
> 而且日志里**不一定有 error**。

#### 6.5.1 判据 1：字典只从 `Packs/<lang>/*.jsonl` 读 —— 平铺在 `Packs\` 根下的文件等于没装

- 代码事实：`src/UI18n.Runtime/ConfigLoader.cs` 的 `LoadPacks` 用
  `Directory.GetFiles(dir, "*.jsonl", SearchOption.TopDirectoryOnly)` 扫 `Packs/<lang>/`（第 156 行），`dir` 由语言候选拼出
  （`zh-cn` → 先试 `Packs/zh-cn`，再试 `Packs/zh`）。
- 踩过的坑：早期实现平铺读 `Packs\` 根下的 `*.jsonl`，而部署按契约把包放在 `Packs\<lang>\` → **一条都读不到，字典恒空**。
  症状不是崩溃，是「patch 装上了、界面全英文」。
- 自证（三条日志，缺一条就是没读到）：
  - 正面：`pack loaded: zh-cn/RP-1.jsonl, entries=+3`（每个文件一行）
  - 正面：`dictionary: entries=N, parseErrors=0`（N > 0，且 parseErrors 必须是 0）
  - 反例：`no pack dir for language=zh-cn (looked for … under …), dictionary is empty` / `no *.jsonl in …` / `packs dir not found: …`
- **判据**：装完之后 `Get-ChildItem GameData\UI18n\Packs\<lang> -Filter *.jsonl` 至少一个文件，且日志里 `pack loaded:` 的行数与它**一样多**。

#### 6.5.2 判据 2：源产物（`pool.jsonl` / `glossary.jsonl` / `inventory.json`）绝不许进 `Packs\`

- 代码事实：解析器要求 `h`（`src/UI18n.Core/Dict/JsonLineReader.cs:90`）与非空 `t`（`:102`）；源产物没有 `t`（它们有 `text`），
  于是**每一行都是 ParseError**。
- 实测（把已编译的 Core 拉进来灌真实文件，不等游戏启动）：

| 文件 | 行数 | entries | parseErrors |
|---|---|---|---|
| `packs/pool.jsonl` | 12,792 | **0** | **12,792** |
| `packs/glossary.jsonl` | 2,126 | **0** | **2,126** |
| `src/UI18n.Runtime/smoke/_smoke.jsonl` | 34 | **34** | **0** |

- 踩过的坑：旧版部署会把 `packs\{pool,glossary}.jsonl` 当字典拷进 `GameData\UI18n\Packs\` → 每行 ParseError、字典恒空；
  因为「文件明明在」，排障时最容易被误判成编码问题。
- **判据**：`parseErrors == 0`。出现 `parseErrors == 文件行数` 时，**先怀疑装错了文件，不要查编码**。

### 6.6 PackLocator：Packs 布局判据的代码化（事故回归锁）

**事故一句话**：Runtime 里手写的包发现逻辑用 `Directory.GetFiles(Packs, "*.jsonl", TopDirectoryOnly)` 平铺读根目录，
与 D35 契约 `Packs/<lang>/<modId>.jsonl` 不符 —— 于是**按契约放的包一条都读不到、字典恒空、patch 恒 0**。
这一层（net472 + 依赖游戏侧程序集）在本机没法单测，所以它是**装进真游戏才发现的**；
现在把纯路径计算搬进 Core，让「优先级 / 回退 / 平铺文件永不读」三件事能被单测穷举，不会再退回「装进游戏才发现」。

| 文件 | 大小 | 作用 |
|---|---|---|
| `src/UI18n.Core/Dict/PackLocator.cs` | 25,817 B | 实现：语言归一化 / 候选回退 / 目录选择 / 文件枚举 / 诊断 |
| `src/UI18n.Core/Dict/README-PackLocator.md` | 7,809 B | API 契约、优先级规则、与提案的差异、Runtime 接线示例 |
| `tests/UI18n.Core.Tests/PackLocatorTests.cs` | 23,563 B / **81 例** | 穷举每一条规则，含 2 条事故回归锁 |
| `tests/UI18n.Core.Tests/PROPOSAL-PackLocator.md` | 21,075 B | 提案与事故复盘（写代码前的原始设计） |

API（`namespace UI18n.Core.Dict`）：`NormalizeLanguage` / `LanguageCandidates` / `SelectLanguageDir`（纯函数版 + I/O 版）/
`ListPackFiles` / `Resolve` → `PackResolution`（状态 + 命中目录 + 文件 + 诊断 + `Describe()`），
状态枚举 `PackDirStatus { Found, PacksRootMissing, LanguageDirMissing }`。

**写死的七条规则**（细节见 `README-PackLocator.md` §2）：

1. 归一化 Trim → `_` 换 `-` → ToLowerInvariant（Invariant，避开土耳其 i）。
2. 候选：完整标签在前、主语言在后（`zh-cn` → [zh-cn, zh]），多段只回退一次。
3. **单向回退**：`zh-cn` 能落到 `zh/`，`zh` **不会**升到 `zh-cn/`。
4. 目录匹配先 Ordinal 精确、再 OrdinalIgnoreCase，返回磁盘真实大小写（不依赖文件系统行为）。
5. 文件枚举 `*.jsonl`、不递归、跳过 0 字节、按文件名 **Ordinal** 升序（顺序必须确定 —— 后写覆盖先写）。
6. **平铺文件永不读**：根下的 `*.jsonl` 只进 `FlatFileCount` 诊断字段。
7. **不抛异常**：根不存在 / 无权限 / 非法字符 / 语言为 null 一律返回状态枚举（红线 6：失败只 log 不抛，但必须能计数）。

**两条事故回归锁**（它们红了就说明又退回「装进游戏才发现」）：
`Resolve_FlatPacksUnderRoot_AreReportedNotSilentlyLoaded` —— 只有平铺包时必须给 `LanguageDirMissing` + `Files` 空 + `FlatFileCount==2`；
`Resolve_FlatPacksDoNotHideRealLanguageDirectory` —— 平铺包与真语言目录并存时只读真目录。

> **状态（v0.8 更新）：已实现 + 已单测（81 例全绿）+ Runtime 已接线，但接线后的构建还没进过游戏。**
> `src/UI18n.Runtime/ConfigLoader.cs` 第 134 行现在是 `PackResolution packs = PackLocator.Resolve(root, language);`，
> 第 123–124 行的注释把「不许再自己拼 Packs 路径或判断 `Directory.Exists`」写成硬规矩（那正是 P1 事故的复发路径）；
> `packs.FlatFileCount > 0` 时打 Warn「flat *.jsonl file(s) directly under … are ignored」当常驻自检。
> Runtime 内 grep `PackLocator` 命中 **4** 处（`ConfigLoader.cs:123/134`、`README.md:198/290`）。
>
> **但接线是在 round 1 进行中做的**（`ConfigLoader.cs` mtime 09:07:46、`build/bin/Release/net472/UI18n.Runtime.dll` 09:08:58 / 41,984 B），
> 而 round 1 跑的是部署里 07:58 的旧 DLL（42,496 B，sha256 `4F43A79199947A45…`）——**那份 DLL 里根本没有 `PackLocator` 这个类型引用**（对 DLL 做字符串扫描：
> 旧 DLL 无 `PackLocator`、无 `flat *.jsonl` 诊断串；现行构建两者都有）。所以 round 1 证明的是「按契约目录放包 → 运行时读到 10,024 条」，
> **不是**「PackLocator 这条新路径被真游戏验过」。后者要等 round 2（D38：接线后的产物验证过才出最终 zip）。

#### 6.7.2 事故：staging 改写把 `UI18n.cfg` 的键名吃掉

`UI18n.cfg` 里有一行（缩进是 TAB）`Version = 1.0.0`，出包时要把版本号改成本次的 `-Version`。第一版实现用正则替换：

```powershell
$cfg = $cfg -replace '(?m)^(\s*Version\s*=\s*)\S+\s*$', ('1' + $Version)
```

**现象**：zip 里的 `UI18n.cfg` 那一行变成孤零零的 `11.0.0` —— `Version =` 键名整段消失；而仓库模板 `GameData/UI18n/UI18n.cfg` 与部署目录里的那份都是好的（`Version = 1.0.0`）。也就是说**只有出包这一步会弄坏它**，而当时七条内容断言全绿（它们只查「文件集合」：不许有 Probe / `_smoke` / `.pdb` / `.old-` / 内部目录 / pool / glossary / 多余 dll）。

**根因**：本意是 `'${1}' + $Version`（替换串里引用第 1 个捕获组），但这段代码是用 JS 模板串生成 PowerShell 的，`${1}` 被**外层**插值成了字面 `1`，替换串于是变成 `'1' + $Version` —— 捕获组没了，`Version = ` 被替换成 `1`，后面接 `1.0.0` 就成了 `11.0.0`。

**修法**（现在 `build-release.ps1` 里的写法）：不用 `-replace` 的组引用，改 `[regex]::Matches` 拿到每个 `Match`，按 `Match.Index` / `Match.Groups[1].Value` 做**纯字符串拼接**；并且**版本行必须恰好 1 行，否则 `throw`**（0 行 = 模板被改过、2 行 = 有两处版本号，都拒绝出包）。

**新增的三条断言**（`release-checks.ps1`，读的是**改写后**的产物）：

| # | 断言 | 抓的就是这个事故 |
|---|---|---|
| 10a | `UI18n.cfg` 的版本行恰好 1 行，且值 == `-Version` | 键名被吃掉后值不对、行数也不对 |
| 10b | 不许出现「裸版本号」畸形行（`^\s*[0-9]+\.[0-9]+\.[0-9]+\s*$`） | 直接拦 `11.0.0` 这种形态 |
| 11 | `UI18n.version`（KSP-AVC）的 `VERSION` == `-Version` | 同一类：改写 / 注入后没校验语义 |

**教训**：原来的断言只查了「**文件集合**」，没查「**文件内容**」。staging 阶段的任何**改写 / 注入**（版本号、占位字段、时间戳）都必须配一条**读改写后产物、校验语义**的断言 —— 否则「断言全绿」与「产物正确」是两件事。

**方法论（这次是怎么抓到的）**：七条断言全绿、`manifest.json` 四字段全对、DLL 三方一致也全对，**是 Lead 手工把 zip 解开看 `UI18n.cfg` 内容才发现的** —— 自动化断言当时没有任何一条会去看那个文件里面。完整复盘在 `src/UI18n.Runtime/README.md` §10.9（`### 10.9 教训：断言查了「文件集合」，没查「文件内容」`）。

### 6.8 验证轮（round）的取证与读日志：九个坑

验证轮最容易出的问题不是「插件坏了」，而是**证据本身是假的**。下面九条是 round 1 / round 2 / round 9 / round 10 真踩到的（坑 6 在出包侧、坑 8 在守护脚本侧，错法同源：把「我做了这个动作」当成「证据成立」），写在前面免得下一轮再交一次学费。

**坑 1 · 截图拍到了桌面，不是游戏。** round 1 的 `verify-20261023-090354.png`（764.4 KB, 3440x1440）拍下来是桌面 ——
截图那一刻 KSP 是 `iconic=True`（最小化，窗口矩形 `-32000,-32000`），`CopyFromScreen` 抓的是屏幕，不是游戏窗口。
正确姿势（Lead 手工复核用的就是这条）：`ShowWindow(SW_MAXIMIZE)` + `SetWindowPos(HWND_TOPMOST)` → 等 2 s → `CopyFromScreen`，
产物 `build/shots/verify-topmost-092820.png`。
**教训**：截图取证必须**先断言目标窗口在前景且未最小化**，断言不过就打 `shot: SUSPECT` 并让本轮判为「证据不足」——
否则「我们拍了张图」是一句没有信息量的话，而且看起来像证据。

**坑 2 · 探针 auto-stop 抛 `System.ArgumentException`，是探针自己的问题。** 日志第 295 行：

```text
[ERR 09:21:43.298] [UI18n] [probe] window contents failed: System.ArgumentException: Getting control 6's position in a group with only 6 controls when doing repaint
```

它只发生在探针 DLL 内（探针到点自己停止绘制，GUILayout 的组计数与上一趟 Layout 对不上），**运行时零影响**，探针随后已从磁盘移除（第 38 行 `probe removed from disk: True`）。
看到这一条不要当成产品故障去查 Runtime。

**坑 3 · 「错误行」统计有假阳性。** round 1 的汇总打印 `UI18n error lines: 3`（第 296 行），但其中 2 条是字典装载行（第 297–298 行），
只因为它们含有 `parseErrors` 这个词就被 `error` 关键字捞进来了；真正的 ERR 只有坑 2 那一条。
**教训**：读 `error lines` 之前先看那几行原文，别把计数当故障数。

**坑 4 · 启动时间是观测值，不是耗时基准。** round 1 的 `verdict=mainmenu after 481s (log 24,882,195 B)`（第 28 行）比历史慢，
但这一轮装了探针 DLL、且 42 个包 / 10,024 条字典是首次加载，**没有做对照** —— 写文档、下结论时只能写「本轮观测 481 s，归因待 round 2」。

**坑 5 · dwell 死锁：进了主菜单，脚本却空转到被人工 kill。** round 2 的
`[09:47:31] verdict=mainmenu after 416s (log 24,876,024 B) -> dwell 60s`（`reports/verify-20261023-094034.log` 最后一行）
之后**再没有任何输出**，直到 09:53 人工 kill。
根因：dwell 判断原来嵌在 `if ($tail -match 'to MAINMENU|MAINMENU to')` 里面，而 `$tail` 只是 `Get-Content -Tail 300`；
KSP 进主菜单后仍每 20 s 写一次 patch stats（其它 mod 也在刷日志），那行 `MAINMENU` 滚出 300 行窗口之后条件永不成立 → dwell 永不触发。
修法（已落在 `_scratch/p1/round.ps1` 09:59 版：事故注释 `:104–107`、新逻辑 `:121–134`）：**判定一次就把 `$mainmenuAt` 锁住**，
把 dwell 检查提到 `-match` 外面。
**判据**：日志里出现 `-> dwell 60s` 之后，60 s 内必须再出现后续行（截图 / 汇总 / `final dump`）；
只有那一行、之后全空白 = 死锁，别坐着等 deadline。

**坑 6 · 从脏工作树出包。** 现象：`dist/UI18n-1.0.0.zip` 里两个 DLL 内嵌 `1.0.0+fc1c2b20d7f53ef8e071d8de2ed97fdaa266b850`，但那份 DLL 是**工作树脏的时候**编出来的 —— 构建时 `HitSampleLimit` 等改动还没提交，`fc1c2b2` 里**没有对应源码** ⇒ 二进制声称的 commit 编不出这份字节。
根因：.NET SDK 把 `SourceRevisionId`（= 构建时的 `git rev-parse HEAD`）追加进 `InformationalVersion`；工作树脏并不影响它取 HEAD，于是「源码不完整的构建」被标成了一个看起来正常的 commit。
**判据**：出包前 `git status --porcelain` 必须为空，**且** 两个 DLL 内嵌的 sha 等于 `git rev-parse HEAD`（读法见 §6.7.1）。守卫在 `build-release.ps1`：加 `-AllowDirty` 开关、**默认拦脏树**（本轮由 core-engineer 落地）。
**教训**：「我编了」不等于「发布物来自这个 commit」—— 脏树构建出来的包，内嵌 commit 是假的。
**同源的第二种形态**：断言只查「文件集合」不查「文件内容」⇒ staging 改写把 `UI18n.cfg` 的键名吃掉，七条断言全绿却出了坏包（§6.7.2）。

**坑 7 · 截图恢复窗口用错了 Win32 常量：`SW_MAXIMIZE` 对已最小化的窗口无效。** round 9 之前的截图流程写的是
`ShowWindow(hwnd, SW_MAXIMIZE)`（= 3），对**已最小化**（`IsIconic=True`）的窗口不起作用 —— 窗口仍是 `iconic`，
后续 `CopyFromScreen` 抓到的还是桌面（与坑 1 同一种假证据，但这次「看起来我们已经调用了 ShowWindow」）。
正确做法：**先 `ShowWindow(hwnd, SW_RESTORE)`（= 9）把窗口从最小化状态恢复成普通状态**，再
`SetWindowPos(hwnd, HWND_TOPMOST, …)` 提到前景，等 2 s，然后 `CopyFromScreen`。
**判据**：截图前断言 `IsIconic(hwnd) == False` **且** 采样点属于目标窗口 —— round 9 的日志就是
`shot: OK (KSP restored and on top: 9/9 sample points belong to it)`、`exit=0, suspect=False`，产物
`build/shots/verify-zhcn-r9-il-20261023-144202.png`；断言不过就打 `shot: SUSPECT` 并把本轮判为「证据不足」。
**教训**：窗口的「恢复」与「置顶」是两件事，常量选错时**调用会返回成功但不产生效果** —— 只有事后断言能发现。
**round 10 复验**：这一条现在还会以「恢复成功、但抓图那一刻又缩回去了」的形态出现 —— 见坑 9。

**坑 8 · 守护脚本判「到主菜单」只能看本次启动之后新增的日志。** 用整文件 `Select-String 'to MAINMENU'` 会被**上一局**留下的行立刻命中。
`_scratch/p1/watch-restore-shot.ps1` 的注释记着实测（第 42–45 行）：「只看『本次启动之后新写入的内容』：KSP.log 里还留着上一轮或玩家上一局的 MAINMENU 行，
整文件 `Select-String` 会在启动瞬间误判『已到主菜单』，然后截一张加载条 / 桌面的图」。它的做法是先记基线 `$baseLen = $len`，
之后只扫新增的那一段（`baseline log length=N (only new output counts)`），命中才记 `$menuAt`。
**判据**：日志里必须能看到基线行且 N > 0；没有基线就别信「已到主菜单」。
**教训**：日志是**累积**文件，任何「扫全文」的判据都会被历史行骗 —— 判据要写「本次新增」。

**坑 9 · 恢复了窗口、也置顶了，抓图那一刻它可能又被最小化了。** round 10 的 `round.ps1` 自己那张截图就是这种：
`shot: hwnd=… visible=True iconic=True rect=-32000,-32000,… foreground=False fgWindow="QQ"` → `restore attempt 1 (WM_SYSCOMMAND SC_RESTORE + ShowWindow SW_RESTORE)` →
`after restore attempts=1 iconic=False rect=0,0,3440,1440` → `coverage points=9/9 belong to KSP pid=57540`，
**但** 紧接着 `pre-capture iconic=True` ⇒ 判 `shot: SUSPECT (KSP still minimized at capture time (restore attempts=1, exitedDuringRestore=False))`、`shot: exit=3, suspect=True`。
与坑 7 的区别：坑 7 是**常量用错、恢复根本没发生**；坑 9 是**恢复发生了、之后又被抢走**（外部窗口抢焦点、游戏自己缩回）。
**判据**：`shot: SUSPECT` 那张图一律不能当视觉证据；真证据用守护脚本拍的 `build/shots/r10-il.png`（3,912,565 B，`iconic=False` 的真实截图）。
**教训**：「我调用过恢复 API」不是证据，**抓图前一刻的 `IsIconic` 才是**。

### 6.9 deploy 的版本戳：`-Version` 与「验的字节 ≠ 发的字节」

**事故（2026-10-24 发现，`29ffa5c` 修掉）**：`deploy.ps1` 原来**自己跑** `dotnet build`（原第 88 行），且**不传** `-p:Version`。
发布流程是「先用 `-p:Version 1.1.0` 构建发布版 → 再跑验证轮」；可一跑 `deploy.ps1 -Install`，它就按默认版本重建了一遍，
把 `build\bin\Release\net472\` 里刚构建好的发布版产物**覆盖成默认版本戳**。

| 环节 | 产物 | 版本戳 |
|---|---|---|
| `build-release.ps1` 打进 zip 的 | `build\bin` 的那份 | `1.1.0+29ffa5c…` |
| `deploy.ps1` 装进游戏、验证轮实际跑的 | 被按默认版本重建的那份 | `1.0.0+<另一个 commit>` |
| 差在哪 | **字节不同**、`ProductVersion` 不同 | ⇒「发布物是验证过的产物」（D38）**在字节层面不成立** |

**为什么「默认」是 1.0.0（可验证）**：`Directory.Build.props` 里**没有** `Version` 属性，所以
`dotnet msbuild src\UI18n.Runtime\UI18n.Runtime.csproj -getProperty:Version` 输出 `"Version": "1.0.0"`。
即「不带 `-p:Version` 的构建」= 1.0.0 戳 —— 这就是覆盖的机制，不是偶发。

**`29ffa5c` 的改法（四条，全部落在 `src/UI18n.Runtime/deploy.ps1`）**：

| # | 改了什么 | 现在的行为 |
|---|---|---|
| 1 | param 加 `[string]$Version = ''`（第 39 行） | 可选：不传就还是老行为（开发期部署）；发布前验证轮**必须**传 |
| 2 | 格式校验（第 94 行） | 不是 `X.Y.Z` 直接 `throw "[deploy] -Version 必须是 X.Y.Z，实际 '…'"` |
| 3 | 构建参数改数组（第 92–98 行），有 `-Version` 时追加 `-p:Version={0}` | 部署构建与发布构建用**同一个**版本号 |
| 4 | 构建后回读 `VersionInfo.ProductVersion`（第 102–108 行），不以 `$Version` 开头就 `throw` | **不留静默失败路径**：戳不对当场炸，不会等出包才发现字节不同 |

**规矩：发布前验证轮的唯一正确命令**

```powershell
pwsh -File src\UI18n.Runtime\deploy.ps1 -Install -Version 1.1.0
```

（出处 `src/UI18n.Runtime/README.md:189–191`，注释原文：「否则 deploy 会用默认版本重建，验的那份字节 ≠ 发的那份字节」。）

**三条判据（缺一条就说明「验的不是发的」）**：

| 判据 | 怎么查 |
|---|---|
| 部署 DLL 与 `build\bin` 的 `ProductVersion` 都等于发布版本、且 commit 相同 | `(Get-Item <dll>).VersionInfo.ProductVersion` → `1.1.0+29ffa5c548fdf5855f8666650717bcd422995a25` |
| 部署 DLL 与 zip 内 DLL 逐字节相等 | `Get-FileHash`：Core 50,176 B `F46E15985C03D0A9…` / Runtime 58,368 B `DCD7C5DABD785BEF…`（§6.7 的 D38 表） |
| `git describe --tags --exact-match HEAD` == 发布版本 | `29ffa5c` → `v1.1.0` |

**反例（别再踩）**：验证轮报告里 `ready:` 那行的 `version=` 前缀与 `dist/*.zip` 的版本号不一致 ⇒ 这一轮白跑；
round 10 的原文是 `version=1.1.0+29ffa5c548fdf5855f8666650717bcd422995a25`，与 1.1.0 的 zip 对得上，这是它算数的原因。
