# 12 · 上报闭环设计（玩家上报 → 审阅 → 进包）

> 状态：设计定稿（v1.7 / 2026-10-29）。本文是 docs/11 §6 中 **M4-a** 的交付物，也是 M4 的唯一阻塞点 B18 的解法。
> 结论先说：**不建服务端**，用 GitHub Issue 当传输层。客户端只负责「把候选整理成一段可粘贴的文本 + 一个可点的链接」，不持有任何网络协议、密钥或账号。

## 12.1 目标与非目标

目标（对应 docs/00 §11 的 M4 验收）：玩家看到未翻译文本 → 在游戏里点两下 → 一个带候选数据的 Issue 出现在仓库 → 维护者审阅合并 → 下一个语言包更新里就有这条，闭环在**一周内**。

非目标：

- 不做自动后台上传（无服务端、也不该在玩家不知情时把游戏内文本发走）。
- 不做在线增量接口（语言包热更新走已有的 Update 通道，见 12.7）。
- 不做翻译众包平台（Issue 的评论就是众包，够用）。
- 不在客户端做机器翻译（LLM 只在 CI 的 translate job 里跑，见 docs/11 §5）。

## 12.2 传输层决策：GitHub Issue（B18 定案）

选它的理由：

1. **零运维、零成本、零合规负担**：没有服务器就没有可用性、备份、被攻击、GDPR 之类的问题需要处理。
2. **身份与限流现成**：GitHub 账号承担了「谁提交的」和「刷屏怎么办」，不用自己写验证码、配额、封禁。
3. **审阅流程就是 PR review**：维护者能逐条改字、能拒、能要补充，比自建后台的审核界面便宜一个数量级。
4. **可追溯**：Issue 与最终合并的提交通过 `Refs #<n>` 串起来，事后能查这条译文从哪来、谁提的。

代价（明确接受）：

- 上报需要玩家有 GitHub 账号。**兜底**：面板同时提供「导出到文件」，玩家可以把文件贴到贴吧/QQ 群，由有账号的人代提。
- Issue 正文是纯文本，不适合承载几万条候选。**兜底**：正文上限见 12.4，超了要求分包，一包只放一个 mod 的候选。

退路：如果将来真的需要匿名上报（例如玩家基数大到 GitHub 成为瓶颈），把 12.4 的 bundle 原样塞进任意 HTTP 端点即可 —— 协议已经是「自包含 JSON 文本 + 自校验 hash」，与传输无关。

## 12.3 端到端流程

1. 运行时捕获未命中文本，写进 `PluginData/UI18n/submission-<session>.jsonl`（**已实现**：src/UI18n.Runtime/Submission/SubmissionExporter.cs，`options.Language` 默认 zh-cn）。
2. 玩家在设置面板点「上报未命中文本」（M4-b）。
3. 客户端把当前会话候选整理成 bundle：去重、排序、限额、脱敏（M4-b），得到一段文本。
4. 客户端拼出 Issue URL（标题 + body 预填 + `labels=capture`），用 `Application.OpenURL` 打开浏览器（M4-b）。
5. 玩家在浏览器里看一眼内容、点 Submit。
6. 维护者跑 `tools/accept-submission-issue.ps1 -Issue <n>`（**已实现**）拉取并校验（M4-d 补校验规则）。
7. 校验通过的候选进 `packs/capture-candidates.jsonl`，经 translate job 出中文，合进 `packs/zh-cn/*.jsonl`。
8. 下个语言包更新（已有 Update 通道）到达玩家机器。

## 12.4 上报载荷契约（bundle schema `ui18n-submission/1`）

复用 tools/i18n_tools/submission.py 已定义的形状（它的 `validate()` 已经在查脱敏与字段完整性），不再另造一套：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `schema` | string | 固定 `ui18n-submission/1` |
| `session` | string | 8 位十六进制会话 id（无机器信息） |
| `lang` | string | 目标语言，`zh-cn` |
| `mods` | array | 上报涉及的 modId 列表（必须在 packs/mods.json 里） |
| `entries` | array | 候选条目，见下 |

`entries[i]`：

- `h`：16 位小写十六进制，**必须等于** `fnv.hash_text(textnorm.normalize(s))`，接收侧重算校验（防手工编辑出错）。
- `s`：原始渲染串（已脱敏）。
- `n`：归一化串（NFKC + 空白折叠）；缺省时接收侧自己算。
- `k`：KSP 本地化键（`#LOC_...`）或空。
- `mod`：调用方 modId，来自程序集名前缀，空则记 `UI18n-Unattributed`。

限额（客户端强制、接收侧再查一次）：

- 单次上报 ≤ **400** 条候选；issue 正文 ≤ **60,000** 字符（GitHub 上限 65,536，留余量）。
- 超出时按 mod 分包，并要求玩家分多次提交；客户端在面板上直接说明「本次只带了前 400 条，还有 N 条」。

隐私红线（写进 `_check_redactions` 的拒绝清单）：

- 不含绝对路径（`D:\`、`/home/`、`C:/Users`）、用户名、存档名、坐标、日志行。
- 不含机器标识（GUID、MAC、IP、安装路径）。
- `s` 里出现上述形态时**整条丢弃**而不是打码（打码后的串既不能查字典也不能定位）。
- 允许携带的宿主信息只有三项：OS 家族、KSP 版本、UI18n 版本。

## 12.5 客户端实现（M4-b / M4-c）

落点：`src/UI18n.Runtime/Submission/` 下新增 `SubmissionReport.cs`（组 bundle 与正文）+ `SubmissionIssue.cs`（拼 URL 与打开浏览器）；面板在 `src/UI18n.Runtime/UI/PrefsPanel.cs` 已有的「未命中」区块加一个按钮。

约束：

1. **不引入网络栈**。不 `UnityWebRequest`、不 `HttpClient`，只用 `Application.OpenURL` —— 这样上报功能不可能因为网络/证书/代理而在玩家机器上出错。
2. **正文过长不截断成半条**：URL 超过 `SubmissionReport.LimitUrlChars`（7000）时不再把正文塞进 URL，改由面板提示「把 bundle 文件拖进表单」——已落地的形态是 `BodyInUrl=false` + `NeedsFileFallback`，不再另建 report 文件（正文与 bundle 说的是同一批条目，两份文件反而让玩家挑错）。
3. **按钮位置与文案走既有 T() 机制**，不在代码里写中文（与 Fix-2 的结论一致）。
4. 上报动作前后各打一行 `Log.Info`（条数、字节数、URL 长度），方便玩家截图反馈失败原因。

## 12.6 接收侧实现（M4-d）

`tools/accept-submission-issue.ps1`（默认 `-Repo DiaoDaiaChan/KSP_UniversalI18n`）本身不做判定，四项校验全部落在 `tools/i18n_tools/submission.py` + `tools/i18n_tools/api.py`（**已落地**，v1.7）：

| # | 校验 | 落点 | 失败形态 |
| --- | --- | --- | --- |
| 1 | `h` 重算一致 | `submission.py` `_check_entries`（`fnv.hash_text(textnorm.normalize(s))`，与 C# 同一算法） | `gate / submission-hash-mismatch`，exit 4，details 带两个 h |
| 2 | `mod` 必须能查到 | `api.known_mod_ids()`（= `packs/mods.json` ∪ 现有包文件名）→ `validate(known_mods=…)` | `gate / submission-mod-unknown`，exit 4 |
| 3 | 与语言包去重 | `api.pack_hashes()` → `plan(covered_h=…)` → `merge_candidates`（已覆盖的 h 不插行） | 不算错，`covered:true` |
| 4 | 重复投递 | `submission.existing_state()` + index/meta 的 `bundleSha256` | 同内容 → `already:true` exit 0（一个文件都不写）；同 id 不同内容 → `gate / submission-id-conflict` |

白名单只来自数据文件（`packs/mods.json` ∪ 包文件名），代码里不点名任何 mod（审计 Fix-2 的口径）。

校验产物：`packs/capture-candidates.jsonl` 追加行 + `packs/submission/<id>/` + index.json + journal 事件；issue 回评论（`gh issue comment`）由 ps1 的 `-Comment` 控制。

## 12.9 风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| 1 | Issue 正文被 GitHub 截断 | 客户端硬限 60,000 字符；超出转文件 + 拖拽 |
| 2 | 玩家贴了含路径的文本 | 接收侧 `_check_redactions` 整条丢 + 在 issue 里回评论说明原因 |
| 3 | modId 归错（捕获时调用方是第三方窗口） | 保留 `UI18n-Unattributed` 伪 mod；面板里可手工改归属（已有 DisplayName 机制） |
| 4 | 刷屏 | GitHub 限流 + 维护者关 issue；候选进 `capture-candidates.jsonl` 前要人过一遍 |
| 5 | 上报与隐私承诺不符（未来加字段） | 字段表在本文与 docs/10 双处维护，任何新字段必须在两处同时出现 |
